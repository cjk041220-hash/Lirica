# 一、 第一轮现状深度自查：四大系统级断层剖析

在第一轮迭代中，我们完成了 Phase 0（新基建）到 Phase 5（操控基座）共 249 个单元测试的全绿验收。然而，深度的全景代码与调用链审计清晰表明：**当前系统仅达成了“子模块单点纯算法与数据实体”的沙盒自洽，在真实的“端到端业务接线（End-to-End Wiring）”和“复杂运行态环境”下，存在四大系统级结构性断层。**

```
                    ┌────────────────────────────────────────────────────────┐
                    │               第一轮代码现状：四大系统级断层              │
                    └────────────────────────────────────────────────────────┘
                                                 │
         ┌───────────────────┬───────────────────┴───────────────────┬───────────────────┐
         ▼                   ▼                                       ▼                   ▼
    【断层一：P0】       【断层二：孤岛】                        【断层三：脱节】    【断层四：消化不良】
   感知与接地坐标断层   Phase 5 操控无总控调度                  主动性未接管悬浮窗  记忆无整理/无Tool
   (Snapshot无坐标,     (Intent/Gesture/Grounding/Gatekeeper    (Overlay依然暴力    (Top-5暴力拼接,
    Grounding要坐标)     从未被 UI/Agent 实例化和调用)            轮询Dao,总线闲置)  Worker仅机械写日记)
```

### 1.1 【P0 级致命断层】感知-接地坐标语义鸿沟
*   **代码实测现状**：
    *   感知侧 `AccessibilityNodeSnapshot`（`app/src/main/kotlin/com/xiaoxi/android/perception/model/AccessibilityModels.kt:17-27`）仅有 `text / contentDescription / className / viewId / isClickable / isEditable / isPassword / isFocused / depth`，**没有任何物理屏幕坐标（bounds）字段**；
    *   `NodeExtractor.kt:53-57` 专为低能耗后台感知设计，遍历时不调用 `getBoundsInScreen`，且实施硬性剪枝：`MAX_DEPTH = 4`，`MAX_NODES = 64`；
    *   执行侧 `HybridGroundingEngine.kt` 进行元素定位时，数据契约 `UiElementNode`（`automation/grounding/GroundingModels.kt:19-27`）**强依赖 `bounds: ElementBounds`**，用以反归一化计算屏幕绝对触控点 `Point2D`；
    *   **全工程全局扫描结果**：没有任何代码负责从 `AccessibilityNodeSnapshot` 转换到 `UiElementNode`。
*   **后果**：自动化操控体系赖以生存的「L0 快路径」（耗时 ≤ 10ms、置信度 0.95 的无障碍精准直达）在数据结构上**完全是一条死路**。上层调度无论如何都会降级到纯视觉 VLM，导致单步延迟从 10ms 恶化至 2000ms+，且大幅增加 Token 消耗与网络抖动失败率。

### 1.2 【结构性断层】Phase 5 自动化执行中枢全员“孤岛化”
*   **代码实测现状**：
    *   `IntentActionDispatcher`、`GestureExecutor`、`HybridGroundingEngine`、`SelfHealingWatchdog`、`FinancialGatekeeper` 5 个核心执行模块仅存在于各自的单元测试中；
    *   主业务装配层（`XiaoxiApplication`、`MainActivity`、`ChatViewModel`、`CompanionOverlayService`、`OverlayExpandViewModel`）**没有一行代码实例化或持有它们**；
    *   `XiaoxiAccessibilityService` 虽配置了 `CAN_PERFORM_GESTURES = true`，但**没有对外暴露实例引用或手势代理接口**，导致 `GestureExecutorImpl` 的 `serviceProvider: () -> AccessibilityService?` 无法取得运行中的无障碍服务实例；
    *   系统缺乏一个顶层的 **GUI Agent 任务状态机调度器**，无法串联“用户意图理解 $\rightarrow$ Intent/UI 路由 $\rightarrow$ 接地定位 $\rightarrow$ 零信任安全审查 $\rightarrow$ 触控/键入分发 $\rightarrow$ 状态核销 $\rightarrow$ 异常自愈”完整闭环。

### 1.3 【交互性断层】主动性裁决总线与伴生悬浮窗“表里不一”
*   **代码实测现状**：
    *   Phase 4 研发了集成打扰代价模型 $Cost_{int}(t)$、内隐动机双门控与每日配额硬限制的 `ProactiveBubbleCoordinator`；
    *   但在 `CompanionOverlayService.kt` 中，悬浮窗在 `onStartCommand` 时直接调用 `expandViewModel?.refreshIcebreaker()`，而该方法直接通过 `unspokenThoughtDao.getTopUrgentThoughts(1)` 裸拉数据弹窗；
    *   **生产环境完全绕过了主动性裁决中枢**，情境打扰代价惩罚与反馈自适应退避在实际运行中全部处于空转闲置状态。

### 1.4 【心智性断层】记忆系统缺乏真实消化与工具调用能力
*   **代码实测现状**：
    *   当前对话层（`XiaoxiLlmClient`、`ChatViewModel`）仅有单向的文本流式聊天，**没有 Function Calling / Tool Use 闭环**，AI 无法根据对话语境发起系统工具调用；
    *   `DualTrackMemoryManager.assembleDynamicContext` 依然是简单的 **Top-5 用户事实 + Top-2 自叙见闻暴力字符串拼接**。一旦数据库条目过百，长上下文检索将出现注意力稀释与幻觉污染；
    *   `AutonomousLifeWorker` 闲时后台虽然已由 WorkManager 注册，但 `DiaryEngine` 只是机械地将当天的聊天记录总结成一篇日记写回数据库，**完全没有进行事实记忆合并、去重、相对时间转化为绝对时间、矛盾仲裁与全局世界观提炼**。

# 二、 双外脑调研的吸收与架构裁决

针对 `AcidGr agent-mobile-use`（Android 底座）与 `Cortico`（Agent Harness）两份深度调研，我们进行严格的事实核验、可行性论证与工程裁决：

### 2.1 吸收 AcidGr：锻造高鲁棒物理执行手脚（坚守日常非 Root 底线）

| 维度 | AcidGr 外部做法 | 小汐 2.0 批判性裁决 | 最终落地设计 |
|:---|:---|:---|:---|
| **执行沙箱** | KernelSU Root + LSPosed Hook `system_server` 绕过 Android 跨屏限制，在隐藏虚拟副屏中操控第三方 App | **坚决否决。**<br>1. 小汐是交付给普通用户的伴生应用，国产日常机 BL 锁死无法 Root；<br>2. Hook `system_server` 必触发银行、微信支付风控，破坏目标场景；<br>3. 强耦合特定 ROM 专属 Jar 包，维护不可持续。 | **纯原生前台协同执行。**<br>在物理主屏上直接执行，配合悬浮执行状态指示、进度流水卡与强二次确认门，打造体贴、透明且符合安全直觉的代行体验。 |
| **感知与执行树** | 单一树 Dump，全量 JSON 递归抓取 | **采纳并升级为双树架构。**<br>感知态与执行态职责不同，不可混用。 | **双树抽样分离：**<br>• 感知态树（`NodeExtractor`）：低功耗、depth≤4、64 节点、无坐标，用于静默感知；<br>• 执行态树（`ExecutionTreeExtractor`）：高保真、300~500 节点预算、带完整 bounds、优先级排序。 |
| **树 Dump 稳定性** | 零窗口重试 3 次；600ms 双轮抓取取优 | **全量采纳。**<br>微信等加固 App 在窗口切换时存在瞬时空树 Bug。 | 引入 `TreeDumpResult` 密封类（杜绝空列表代表失败）；落实 600ms 双轮 Dump 取优与自愈标记。 |
| **截帧与坐标一致性** | 守护进程持有 Surface 直接编 JPEG 80；绝不预降采样 | **全量采纳。**<br>预降采样会导致归一化坐标推算产生非线性整体漂移。 | 建立 `FrameCaptureResult(bytes, widthPx, heightPx, ts)`，严格以真实捕获分辨率作为反归一化基准。 |
| **文本注入** | 剪贴板写入 + `keyevent 279` (PASTE) | **拒绝照搬，改为双轨安全注入。**<br>静默覆盖剪贴板会破坏用户刚复制的重要内容。 | `ACTION_SET_TEXT` 为第一优先级；剪贴板粘贴为降级路径，且**降级前快照备份用户剪贴板，注入后立即恢复**。 |

# 四、 五大核心子系统深度工程规格设计

## 4.1 子系统一：执行态无障碍树抽取与接地桥接中枢 (Helix-Grounding Bridge)

### 4.1.1 核心使命
彻底打通从无障碍服务底层到 `HybridGroundingEngine` 之间的断层，实现 **带真实屏幕物理坐标、高节点预算、具备抗抖动自愈能力的高保真树抽取**。

### 4.1.2 核心数据模型契约 (`automation/grounding/ExecutionTreeModels.kt`)
```kotlin
package com.xiaoxi.android.automation.grounding

/**
 * 执行态专用节点数据模型
 */
data class ExecutionNode(
    val nodeId: String,
    val text: String?,
    val contentDescription: String?,
    val resourceId: String?,
    val className: String?,
    val bounds: ElementBounds,        // 物理屏幕绝对坐标矩形 (left, top, right, bottom)
    val isClickable: Boolean,
    val isEditable: Boolean,
    val isCheckable: Boolean,
    val isChecked: Boolean,
    val isScrollable: Boolean,
    val isEnabled: Boolean,
    val isVisibleToUser: Boolean,
    val isPassword: Boolean,
    val priority: Int,                // 0~5 优先级评分 (输入框=5, 可点击文本=5, 纯文本=4, 容器=1)
    val isLargeContainer: Boolean     // 面积 > 0.5 屏幕的可滚动容器 (用于抑制模型误点击)
)

/**
 * 结构化树抓取显式结果契约 (杜绝以空列表代表异常)
 */
sealed interface TreeDumpResult {
    data class Ok(
        val packageName: String,
        val activityName: String?,
        val nodes: List<ExecutionNode>,
        val totalDiscovered: Int,
        val isTruncated: Boolean,
        val omittedCount: Int,
        val isRecoveredFromRetry: Boolean = false,
        val dumpDurationMs: Long
    ) : TreeDumpResult

    data class Empty(
        val reason: EmptyReason,
        val message: String
    ) : TreeDumpResult

    data class Failed(
        val error: Throwable,
        val message: String
    ) : TreeDumpResult
}

enum class EmptyReason {
    ZERO_WINDOW_TIMED_OUT,   // 窗口切换竞态超时
    PRIVACY_BLACKOUT,        // 银行/密码应用物理安全熔断
    ROOT_NODE_NULL,          // 系统返回 root 为空
    SCREEN_OFF_OR_LOCKED     // 息屏或处于锁屏界面
}
```

### 4.1.3 核心抽取算法与自愈逻辑 (`ExecutionTreeExtractor.kt`)
1.  **节点预算扩展**：设置 `MAX_EXECUTION_NODES = 400`，`MAX_DEPTH = 12`，彻底解决 64 节点在美团、淘宝等复杂国民级 App 上的截断漏目标问题；
2.  **大容器抑制规则**：若节点面积占屏幕面积超过 50%（$Area_{node} > 0.5 \times Area_{screen}$）且具备可滚动特性，将其 `isLargeContainer` 标记为 true，并将 priority 置为最低档（1），防止模型向大容器中心生成无效点击；
3.  **两轮 Dump 自愈与竞态取优**：
    *   第一轮遍历：若提取出的有效可交互节点数 $\le 2$，判定可能遭遇了国产 App 切换切屏过程中的窗口重绘竞态；
    *   触发补偿：非阻塞等待 `delay(600)` 后执行第二轮抓取；
    *   若第二轮节点数明显多于第一轮，采用第二轮结果并标定 `isRecoveredFromRetry = true`；若两轮均为空，返回明确的 `TreeDumpResult.Empty(EmptyReason.ZERO_WINDOW_TIMED_OUT)`。
4.  **桥接至接地引擎 (`toUiElementNodes`)**：

### 4.1.4 剪贴板安全文字注入器 (`TextInputExecutor.kt`)
```kotlin
package com.xiaoxi.android.automation.gesture

import android.content.ClipData
import android.content.ClipboardManager
import android.os.Bundle
import android.view.accessibility.AccessibilityNodeInfo
import com.xiaoxi.android.automation.grounding.ElementBounds
import kotlinx.coroutines.delay

class TextInputExecutor(
    private val clipboardManager: ClipboardManager,
    private val gestureExecutor: GestureExecutor
) {
    /**
     * 安全注入文本：优先无障碍标准接口，降级剪贴板时实施物理快照还原
     */
    suspend fun injectText(
        node: AccessibilityNodeInfo?,
        targetBounds: ElementBounds,
        text: String
    ): Boolean {
        // 优先路径：标准 ACTION_SET_TEXT (零副作用)
        if (node != null && node.isEditable) {
            val args = Bundle().apply {
                putCharSequence(AccessibilityNodeInfo.ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE, text)
            }
            if (node.performAction(AccessibilityNodeInfo.ACTION_SET_TEXT, args)) {
                return true
            }
        }

        // 降级路径：剪贴板注入（严守【剪贴板快照恢复】铁律）
        val originalClip: ClipData? = clipboardManager.primaryClip
        return try {
            clipboardManager.setPrimaryClip(ClipData.newPlainText("xiaoxi_agent_type", text))
            // 先通过拟人化点击获取输入框光标焦点
            gestureExecutor.execute(GestureSpec.Click(targetBounds.centerX.toFloat(), targetBounds.centerY.toFloat()))
            delay(200)
            // 分发粘贴动作
            node?.performAction(AccessibilityNodeInfo.ACTION_PASTE) ?: false
        } finally {
            // 毫秒级恢复用户原本的剪贴板内容，杜绝数据冲掉冒犯
            if (originalClip != null) {
                clipboardManager.setPrimaryClip(originalClip)
            } else {
                clipboardManager.clearPrimaryClip()
            }
        }
    }
}
```

## 4.3 子系统三：深度记忆整理与自叙梦系统 (Subconscious Dream Consolidation Engine)

### 4.3.1 核心使命
把闲时后台的 `AutonomousLifeWorker` 升级为具备自我反思与记忆提炼能力的**自叙梦系统**，解决记忆条目无限膨胀、自相矛盾、缺乏时间维度抽象的核心瓶颈。

### 4.3.2 梦系统的六大整理流水线
```
                                 ┌─────────────────────────────────┐
                                 │   夜间入梦 (Nightly Dream Fork)  │
                                 │   约束: 充电中 + WiFi + 闲时空闲   │
                                 └────────────────┬────────────────┘
                                                  │
         ┌───────────────────┬────────────────────┼───────────────────┬───────────────────┐
         ▼                   ▼                    ▼                   ▼                   ▼
   1. 记录去重合并      2. 相对时间绝对化     3. 矛盾标记消歧       4. 世界观晋升       5. 梦醒生活活水
  (合并重复画像条目,   (将"明天/上周"改写为  (处理冲突信息,标记    (跨天反复出现模式   (提炼 DreamEmergence,
   压缩冗余文本)        具体的 YYYY-MM-DD)   存疑或废弃失效知识)    晋升 WORLDVIEW)     注入未完成念头池)
```

1.  **记录去重合并（Semantic Deduplication & Merging）**：
    *   对近期存入 `user_memories` 的零散事实进行语义聚类（如：用户在不同日子表达了“买新耳机”、“喜欢降噪”、“买了索尼耳机”，聚类合并为“用户拥有索尼降噪耳机并注重音质体验”）；
    *   **架构铁律**：消化、总结、归纳出的内容总量必须少于原始追加的内容总量（反囤积原则）。
2.  **时间重锚（相对时间转绝对时间）**：
    *   白天对话中常出现“我后天要交差”、“下周一去北京出差”等时效性口语；
    *   梦系统根据消息产生的时间戳，统一将其改写为严格的绝对日期（如“用户将于 2026-09-23 前往北京出差”），避免数天后产生理解错位。
3.  **矛盾消歧与认知修正（Belief Revision）**：
    *   若发现新旧记忆冲突（如：旧记录“喜欢吃辣”，新记录“胃炎发作医生叮嘱绝对不能吃辣”）；
    *   将旧条目更新为 `status = 'superseded'`，并将其 `superseded_by` 字段指向新条目 ID，保留认识论来源而不破坏审计轨迹。
4.  **高层世界观晋升（Worldview Promotion）**：
    *   单次对话中发生的偶发事件永远停留在局部记忆；
    *   **只有在不同日期、多个独立情境下反复得到验证的规律**（如用户长期的作息模式、深层的处世哲学、坚固的偏好），才允许被提炼并晋升至 `WORLDVIEW` 核心持久化表。
5.  **梦醒活水浮现（The Morning Emergence）**：
    *   梦系统整理完毕后，生成一段第一人称的思维札记（`surface_emergence`）；
    *   将其作为一条新鲜的 `UnspokenThought` 存入念头池，作为次日白天适时主动破冰的高质量谈资（“昨晚理了理你这几天的日程，今天是不是要去见客户啦？加油哦！”）。

## 4.4 子系统四：地图化记忆注入与上下文交接快照 (Map-Based Memory & Handoff Pipeline)

### 4.4.1 核心使命
摒弃 Top-5 暴力拼接，采用 Cortico 经过验证的 **5 层地图式分层注入** 与 **上下文交接快照机制**，保证模型在海量记忆与长程对话下注意力高度聚焦。

### 4.4.2 记忆分层注入拓扑（The 5-Layer Context Assembly）
```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Level 0: 记忆地图 (Memory Map)                                                                   │
│ - 仅注入记忆领域的顶层目录与索引纲要 (常驻只给地图，细节依靠 Tool 下钻)                        │

│ Level 1: 核心认知与花名册 (Worldview & Roster)                                                  │
│ - WORLDVIEW: 梦系统提炼的高层全局综合认知 (长期稳定的画像)                                      │
│ - ROSTER: 认识的人花名册 (姓名/称谓、与用户的关系、关键注意事项)                                │
├─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Level 2: 备忘与工作记忆 (Memo 3-Tier)                                                            │
│ - 正在进行中 (Resident): 全文常驻 (如正在处理的即时任务)                                        │

│ Level 3: 梦境浮现与自叙经历 (Dream Emergence & Reflection)                                      │
│ - 最近一期夜间梦系统产出的核心反思与小汐自主见闻心得                                            │
├─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Level 4: 即时情境 (Immediate Environment Context)                                               │
│ - 当前时间、电量、前台应用名称、停留时长、脱敏通知摘要                                          │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.4.3 上下文交接快照机制 (Handoff Snapshot)
*   **触发阈值**：当历史会话轮次超过 `MAX_CONTEXT_TURNS = 20` 或 Token 预算超标时触发；
*   **快照提炼**：在丢弃最早的消息前，调用轻量模型为即将出局的历史段提炼结构化摘要（包含：聊到了哪里、未完成的约定、当前情感状态）；
*   **平滑迁移**：将摘要保存为 `handoff_snapshot`，新对话轮次直接以该快照作为开场重锚，彻底消除机械滑动窗口造成的“瞬间失忆”。

# 七、 质量保障、TDD 变异验证与真机复杂场景用例库

### 7.1 工程铁律
1.  **100% Native 原生纯度红线**：严禁引入任何 Python/Chaquopy 依赖，所有状态机、算法与实体均以纯 Kotlin 协程构筑；
2.  **严密 TDD 与破坏性变异测试法网**：
    *   严格执行：**红灯测试 $\rightarrow$ 最小实现跑绿 $\rightarrow$ 故意改坏逻辑做变异验证（确认变红） $\rightarrow$ 恢复全绿 $\rightarrow$ 原子提交**；
    *   重点覆盖：剪贴板还原失败熔断、零窗口重试耗尽兜底、高危操作令牌超时失效、大容器点击抑制。
3.  **用户数据无损与隐私零容忍**：
    *   严禁在未授权情况下覆盖用户剪贴板数据；
    *   密码框整屏物理覆黑（`isPassword == true` 拦截率 100.0%）；
    *   银行类应用整屏熔断不留存任何快照。

### 7.2 真机复杂场景验收用例库
*   **用例 1（切屏与重绘抗抖动）**：模拟应用从后台唤醒到前台瞬间，无障碍根节点在第 0ms 返回 null，在第 400ms 返回有效节点。断言两轮自愈机制成功抓取到第二轮节点，并生成 `TreeDumpResult.Ok(isRecoveredFromRetry = true)`；
*   **用例 2（屏幕缩放防漂移）**：在系统开启 1.25x / 1.5x 显示缩放或存在异形挖孔屏环境下，断言反归一化屏幕物理坐标与真机实际像素中心重合，误差 ≤ 1px；
*   **用例 3（夜间梦系统事实消歧）**：数据库预置“用户喜欢美式咖啡”旧事实；注入今日对话“最近胃酸过多，医生让我改喝大麦茶”。断言入梦后旧事实状态迁移至 `superseded`，世界观更新为“习惯饮用温和无咖啡因茶饮”；
*   **用例 4（高危支付物理熔断）**：模拟用户给出“帮我买这件衣服”指令。Agent 定位到“立即付款”按钮并提取金额，断言 `FinancialGatekeeper` 触发 `CRITICAL_BLOCK`，强制生成一次性二次确认令牌，若用户未在 UI 卡片上授权，手势注入层物理阻断。
