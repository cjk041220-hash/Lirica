## 一、系统哲学与核心设计原则

### 1.1 “全能底座，性格门控”原则 (Omnipotent Base, Persona Gated)
- **能力层（Capability Layer）**：追求 **OS 级全能完备**。涵盖标准 Intent/系统 API、无障碍语义树操纵、Shizuku 提权 shell、后台虚拟屏运行及物理硬件感知；
- **心智层（Mind & Persona Gate）**：负责**动机生成、权限仲裁与人设表达**。Lirica 是一个具有反差萌的年上女性伴生体，她拥有翻江倒海的行动底座，但依据其自尊、亲密阶段与边界感，由心智裁决“应不应该做”、“以什么姿态做”、“如何向用户汇报”；
- **表达与安全解耦原则（P1-3 吸收）**：**人格参数（支配度 D 锁、亲密等级）绝不参与底层的安全通行裁决**。人格只决定“接不接活、用什么口吻说、要不要反问”，底层的安全通行由单一代码事实来源的 `SafetyPolicyEngine` 铁律裁定，杜绝安全规则随心情浮动导致测试矩阵爆炸。

### 1.2 行为的四项刚性契约 (The Four Invariants)
1. **API-First Invariant（API 优先公理）**：能调系统 API/Intent 的绝对不调 GUI；能走语义树节点的不截屏走 VLM；
2. **Zero-Destruction Invariant（零破坏与全通道收口公理 · P0-1 吸收）**：任何涉及资金支付、生物识别鉴权、系统出厂重置、非幂等外部通信（如替用户发送 SMS/邮件），**无论是走 UI 交互还是走 Intent/API 通道，一律经由统一安全闸门硬件级物理熔断**；
3. **Bounded-Loop Invariant（有界自愈公理 · P2-2 吸收）**：
   - 任务步数严格有界（上限 12 步原子循环，自愈重试单任务累计 <= 3 次）；
   - 任务总耗时熔断（硬上限 120 秒）；
   - 超时、迷失或遇到不可恢复异常时触发优雅回退与诚实解释（Honest Narrator），严禁陷入无限重试；
4. **Physical-Reality Invariant（物理现实公理）**：绝不假设手机运行在无限电量、无限内存的云端服务器。系统必须感知温度降频、网络闪断、用户前台抢占与国产 ROM 后台墓碑机制。

## 三、系统分层架构：三层解耦与职责收敛

```
[Layer 3: 心智动力与人设门控层 (Mind & Persona Gate)]
  ├── IntentionArbiter: 用户显式/隐式意图解析
  ├── PersonaActionGate: 年上主导人格表达决策 (决定接不接、怎么说、是否反问；永不决定安全通行)
  └── ConfirmationBroker: 复用现有 AwaitingUserConfirmation 状态流，发起原生卡片二次确认
           │
           ▼ ActionPlan (语义级任务目标)
[Layer 2: 动态编排与自愈决策层 (Orchestrator & Loop)]
  ├── HybridActionRouter: API vs GUI 双轨决策路由
  ├── AutonomousActionLoop: (Coordinator 升级) 单步 Observe -> Ground -> Decide -> Act -> Verify 闭环
  ├── TrajectoryMemory: 经验轨迹库检索、起始页指纹核验与逐步回放
  ├── SafetyPolicyEngine: [P0-1/P1-3 收口] 统管 UI/Intent/只读漫游 的统一安全裁决引擎
  └── SelfHealingWatchdog: 继承现网 3 类异常检测与弹窗自愈，增加用户抢占熔断
           │
           ▼ AtomicAction (原子动作)
[Layer 1: 原生双轨执行引擎 (Capability Engine)]
  ├── [API 通道] 扩展 IntentActionDispatcher (日历/闹钟/设置/手电筒，均过 Safety 闸门)
  ├── [GUI 通道] 维持现网优先级：Shizuku 优先穿透自绘，A11y 手势兜底；中文 100% A11y 铁律
  ├── [环境感知] 扩展 HardwareEnvironmentWatcher (温度/电量/光照 StateFlow)
  └── [视觉反馈] ActionVisualFeedbackListener 解耦抛出触控尾迹与气泡状态
```

## 四、核心子系统一：API-First 双轨执行引擎与 Intent 闸门收口

### 4.1 痛点与 Intent 安全收口（P0-1 落地）
现网 `HelixGuiCoordinator` 的 L0 极速通道和多步循环均未对 `IntentAction` 做任何安全检查，若直接放开外部意图，`SendSms`/`SendEmail` 会成为未授权通信漏洞。
**安全收口规范**：在 `IntentActionDispatcher.dispatch()` 入口强制注入 `SafetyPolicyEngine` 校验，所有系统动作必须具备**“风险等级 + 权限状态 + 闸门规则”**三元组：

| 动作标识 | 原生实现依据 | 风险分级 | 所需权限 / 触发条件 | 闸门与安全策略 |
|:---|:---|:---|:---|:---|
| `SetAlarmAction` | `AlarmClock.ACTION_SET_ALARM` | **低危 (Low)** | `SET_ALARM` | 允许自动放行 |
| `AddCalendarEventAction` | ContentProvider 插入日程 | **低危 (Low)** | `WRITE_CALENDAR` | 允许自动放行 |
| `DialAction` | `Intent.ACTION_DIAL` | **低危 (Low)** | 无 (拉起拨号盘) | 仅预填不自动呼出，放行 |
| `SendSmsAction` | `Intent.ACTION_SENDTO` | **中危 (Medium)** | `SEND_SMS` | 必须经用户二次确认正文 |
| `ToggleFlashlightAction`| `CameraManager.setTorchMode`| **低危 (Low)** | `CAMERA` | 允许自动放行 |
| `AdjustBrightnessAction`| `Settings.System.putInt` | **中危 (Medium)** | `WRITE_SETTINGS` 特殊权限| 引导系统设置授权，放行 |
| `ClipboardReadAction` | `ClipboardManager.getPrimaryClip`| **敏感 (Sensitive)**| **仅限前台/有焦点时可用** | Android 10+ 仅前台悬浮窗聚焦时读取 |

> **Android 10+ 剪贴板现实边界（P2-6 吸收）**：系统级禁止后台服务静默读剪贴板。Lirica 的剪贴板接应仅在两种合法场景触发：① 用户主动分享给 Lirica；② Lirica 悬浮窗或主界面获得系统焦点的瞬间。方案严禁任何静默后台轮询剪贴板的违规设计。

## 五、核心子系统二：动态闭环与经验轨迹进化

### 5.1 从静态列表升级为单步动态 ReAct 状态机
保持聊天层 `NativeToolAgent` 工具面稳定，将 `HelixGuiCoordinator` 内部执行模式升级为自适应闭环：
1. **Observe（多级观测表征 · P2-1 吸收）**：
   - **Level 0 (语义裁剪树，默认优先)**：经过 `ExecutionTreeExtractor` 剪枝与 Token 压缩后的候选交互节点列表（<= 30 项，Prompt 字符数预算 <= 8KB）；
   - **Level 1 (本地 OCR 文本)**：遇自绘/无节点时调用端侧 ML Kit 提取局部文字；
   - **Level 2 (截图云端 VLM，最高代价)**：仅在 Level 0/1 均失效时兜底调用，**单任务硬顶上限 5 次**。
2. **Ground & Decide**：单步决策下一个动作（Click / Type / Scroll / Wait / Back）；
3. **Act**：派发贝塞尔拟人手势或 Shizuku 注入；
4. **Verify（抗噪差量核销 · P2-3 吸收）**：
   - 采用单一收敛的 `StateFingerprint`；
   - 过滤时间戳、电量、轮播等易变文本；
   - 采用 **双采样抗噪机制**：操作后间隔 300ms 两次采样一致才视为页面稳定，结合目标节点状态改变（如 enabled -> disabled）判定动作生效；
5. **Reflect & Self-Healing**：
   - 继承现有 watchdog 弹窗处理（排除授权词）与卡死恢复；
   - 单任务自愈动作累计上限 3 次；任务总耗时超过 120 秒直接熔断触发 `HonestNarrator`。

### 5.2 TrajectoryMemory 经验轨迹生命周期（P1-2 落地）
拒绝盲回放，确立“核验前置、逐步验证、版本淘汰”铁律：
- **存储实体（Room DB v6）**：
  - `macroId`: 唯一 ID；
  - `intentSignature`: 意图签名（如 "PLAY_MUSIC"）；
  - `appPackage` & `targetAppVersionCode`: 目标应用包名与版本；
  - `startPageFingerprint`: 起始页抗噪拓扑指纹；
  - `stepsJson`: 归一化坐标 + ref_id 复合动作序列；
  - `explicitSlotKeys`: 仅支持显式槽位（如搜索词，一期不做模糊参数推断）；
  - `failureCount`: 连续回放失败计数；
- **回放核销纪律**：
  1. **起始页防暴走**：回放第 1 步前重新抓树，必须核验当前页指纹与 `startPageFingerprint` 匹配；
  2. **单步轻量核销**：每步回放仍执行 Verify 差量校验，任一步未生效立即**中止回放、平滑降级为动态 ReAct 循环**；
  3. **版本与淘汰**：目标 App 版本升级直接失效；连续 2 次回放失败自动标记弃用。

## 六、核心子系统三：多通道接地、现网优先级与用户抢占处理

### 6.1 保持现网通道优先级与 CJK 铁律（P1-4 裁决）
方案纠正此前对优先级的误述，**严格维持并巩固现网 `HybridExecutionManager` 经过实测验证的通道逻辑**：
- **点击 / 长按 / 滑动 / 按键**：
  - **Shizuku 可用即优先**：享受进程无创建开销、零延迟、能够穿透部分无障碍自绘屏蔽的优势；
  - **A11y 手势兜底**：Shizuku 未授权或失败时，自动降级为原生无障碍 `dispatchGesture`。
- **文本输入（CJK 铁律）**：
  - **中文与 Emoji 100% 走 AccessibilityNodeInfo 注入**（避免 ADB input 乱码与剪贴板污染）；
  - **纯 ASCII 字符在 Shizuku 激活时可走底层 input**。

### 6.2 用户抢占熔断机制（User Interruption · P2-2 落地）
共享模式下最危险的场景是：Lirica 正在点击，用户突然接管手机打字。
- **实现方案**：
  1. 在 `LiricaAccessibilityService` 中注册 `AccessibilityEvent.TYPE_TOUCH_INTERACTION_START`；
  2. 一旦捕获到物理屏幕上发生未由自动化引擎发起的人工触控事件，`AutonomousActionLoop` 立即暂停派发；
  3. 状态机迁移至 `TaskExecutionState.UserInterrupted`；
  4. 悬浮微表情收敛为安静观察态，待用户停止操作 5 秒或在悬浮胶囊上点击“继续”后再恢复执行，彻底避免人机手势打架。

## 七、现实世界工程兼容性与物理防御体系

### 7.1 国产四大 ROM 墓碑与无障碍保活体系
- **ROM 现实**：MIUI/HyperOS、ColorOS、OriginOS 在后台闲置超时或开启激进省电时，会静默注销无障碍服务；
- **工程对策**：
  1. `LiricaAccessibilityService` 持久句柄探测，断开时联动现有的 `KeepAliveService` 前台服务心跳报警；
  2. 任务分发前快速检测无障碍状态，若失效通过轻量浮窗一键引导进入系统设置重开（`Settings.ACTION_ACCESSIBILITY_SETTINGS`）；
  3. 维持主进程在低 OOM_ADJ 水位，抵御系统进程收割。

### 7.2 分辨率、DPI 漂移与折叠屏适配
- **严禁像素写死**：所有视觉坐标强制走 [0, 1000] 归一化比例空间计算；
- **折叠屏兼容**：屏幕物理状态变化时（Configuration Changed），动态重算真实宽高并刷新接地缓存。

### 7.3 热功耗与电池健康保护
- **电池温度熔断**：监测电池温度，>= 42℃ 时强制熔断连续截屏与后台漫游；
- **电量梯度限流**：电量 < 20% 且未充电时，禁用多模态视觉模型，仅放行轻量 API 动作。

### 7.4 16KB 页大小内存兼容性（Android 15+）
- 全面维持 ONNX Runtime 1.25.0 与 ML Kit 的 16KB 对齐规范，禁止直接载入未适配的旧版原生动态链接库。

## 八、心智门控与双态模式装配（共享 vs 漫游只读）

根据人类架构师定案裁决，构建明晰的双态控制契约：

```
                    ┌──────────────────────────────────────────────┐
                    │        模式切换开关 (UI / 对话决策控制)       │
                    └───────────────┬──────────────┬───────────────┘
                                    │              │
                   [共享模式 SHARED]│              │[漫游模式 ROAMING]
                                    ▼              ▼
                     ┌──────────────────┐    ┌───────────────────────────┐
                     │ 完整操控权限     │    │ 只读拦截 (Read-Only Guard) │
                     │ 允许点击、输入   │    │ 严禁关注/点赞/投币/评论/支付 │
                     │ 执行复合复杂任务 │    │ 仅放行滑动翻页、只读检索   │
                     └──────────────────┘    └───────────────────────────┘
```

- **自主风险交互（伴生沟通机制）**：
  在漫游模式下，当 Lirica 产生探索动机但可能留下播放记录或轻微影响算法时，**严禁自行静默突破只读限制**，必须在主会话流中以成熟年上的口吻向用户提出协商：
  > *“今晚我想去你的 B 站看几篇纪录片，会留下播放历史哦，给看吗？”*
  经用户在对话中确认后，才临时提升单次任务的作用域。

## 九、可观测性与执行轨迹设计（P2-4 落地）

拒绝不可调试的“黑盒自动化”，建立标准执行轨迹：

1. **执行轨迹实体契约（`ExecutionTrace`）**：记录 taskId、goal、mode (SHARED vs ROAMING)、startTime、durationMs、finalState、单步步骤与核销差量、VLM 调用次数（<= 5）、自愈尝试次数（<= 3）；
2. **调试与指标埋点**：
   - 沿用现网 `XiaoxiLog` 环形日志，支持通过 `DiagnosticExporter` 一键导出故障诊断包；
   - 记录 3 项核心指标：单任务端到端成功率、单步中位延迟、Macro 命中率。

## 十、阶段实施路线图与可度量真机验收基准（M5.1~M5.4）

统一采用 **M5.x** 阶段命名（消除历史 Phase 5 命名冲突 · P3-1 吸收）：

### 10.1 阶段规划与交付物
* **M5.0 (前置硬性门禁 · P0-2 吸收)**：
