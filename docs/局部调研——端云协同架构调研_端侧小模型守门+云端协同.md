## 一、背景概述

### 1.1 问题定义

纯云端大模型支撑的 AI 伴生 Agent 存在四个结构性缺陷，这四个缺陷可归为两类：**可用性依赖**与**成本/隐私税**。

| 缺陷 | 性质 | 可量化表现 |
|---|---|---|
| 断网即失效 | 可用性 | 无网络 = 无服务，交互完全中断 |
| 微交互延迟 | 体验 | 单次 WAN 往返在移动网络上不稳定；SWARM-LLM 实测纯云均值延迟 4.47 s、P95 达 11.33 s [S7] |
| Token 开销 | 成本 | 高频低价值交互（寒暄、情绪确认、状态播报）全部走最强模型 |
| 本地感知上传 | 隐私 | 麦克风/摄像头/屏幕内容原始数据出设备 |

需要澄清一个常见误解：**"端云协同"不是把云端能力搬到端侧，而是在端侧建立一层可以独立成立的最小可信系统。** 端侧承担的不是"低配版云端"，而是云端结构上做不好（延迟、隐私）或不应该做（高频、低价值）的那部分工作。

### 1.2 技术前提：1.5B–3B 这一档现在到什么水平

先给出这一档模型的绝对能力基线，后续所有分工判断都建立在这组数字上。

**关键判断（三条）**：

1. **跨代提升大于跨规模提升。** 同参数档位 23 个月里 MMLU-Pro 从 22.9 走到 55.3（Qwen3.5-2B，2026-02），这是单代际最大跃迁。选 2B 模型时"选哪一代"比"选 1.5B 还是 3B"更重要。
2. **考试类基准不构成部署判据。** 1.5B/3B 在 GSM8K 上已经饱和（73–87 分），但在真正决定架构设计的两个维度——多轮工具调用、长程状态回忆——上表现很差（见第三章）。
3. **所有上述数字均为厂商自评，无独立复现。** 且同厂商对同一模型的重新基准存在显著漂移：Qwen2-1.5B 的 GSM8K 在 Qwen2 技术报告里是 58.5，在 Qwen2.5 博客里是 46.9，同一模型、同一厂商、12 分差 [S2]。**引用单一来源的绝对值时必须保留这个不确定性。**

### 1.3 硬件侧的三个认知更新

**更新一：NPU 在 decode 阶段通常不是最优解，甚至常常最差。**

这是本次调研最反直觉、也最有工程价值的一手发现。arXiv:2607.05475（2026-07）在四台骁龙旗舰（Xiaomi 17 / OnePlus 15 / Xiaomi 15 / Xiaomi 14，SM8850/8750/8650）上做了系统测量 [S6]：

| 模型（W4） | 后端/框架 | Decode 吞吐（tokens/s，Xiaomi 17 / OnePlus 15） | Decode 能耗（µJ/token，X17 / OP15） |
|---|---|---|---|
| Qwen2.5-1.5B | CPU / llama.cpp | 51.6 / 55.7 | 1.2e5 / 9.7e4 |
| Qwen2.5-1.5B | NPU / GENIE(QNN) | 23.1 / 23.0 | 4.3e5 / 3.2e5 |
| Llama3.2-1B | CPU / llama.cpp | 76.1 / 72.2 | 1.4e5 / 7.4e4 |
| Llama3.2-1B | NPU / GENIE(QNN) | 25.9 / 26.3 | 2.9e5 / 3.0e5 |
| Llama3.2-3B | CPU / llama.cpp | 29.9 / 30.5 | 2.9e5 / 2.1e5 |
| Llama3.2-3B | NPU / GENIE(QNN) | 8.9 / 12.2 | 7.0e5 / 7.1e5 |

**Prefill 阶段结论完全相反**：同一高通 QNN 后端下，GENIE 的 NPU prefill 达 1463.7 tok/s，MNN 700.9，llama.cpp 仅 115.1——**15 倍差距** [S6]。

原因是阶段性质不同：prefill 是计算密集（compute-bound），适合 NPU 的大矩阵算子；decode 是**内存带宽密集**（memory-bound，逐 token 读 KV cache），而 NPU 偏好静态图、固定 shape，且需要预分配大 context（论文实测 context 从 16 增到 4096 时 NPU decode 吞吐跌 20–23.8%）。

**能耗同样反转**：NPU decode 能耗常为 CPU/GPU 的 2–4 倍（OnePlus 15 上 Qwen2.5-1.5B：NPU 3.2e5 vs CPU 9.7e4 µJ/token）[S6]。

**结论**：不要默认"NPU = 更快更省电"。Phase-aware 调度（prefill 走 NPU、decode 走 CPU）比全图卸载更合理。

**更新二：厂商宣传的吞吐数字与第三方实测存在数量级落差。**

高通官方（Snapdragon Summit 2025-09）：第五代骁龙 8 至尊版 Hexagon NPU 性能提升 37%、能效提升 16%，**30 亿参数模型 token 生成速度达 220 tokens/s** [S27]。而上述学术实测在 Llama3.2-3B 上 NPU 只有 8.9–12.2 tok/s [S6]。

两者不矛盾，但不可直接比较——差异来自量化方案（W4 vs W8/INT2/FP8）、上下文长度、测试负载、后端实现。**跨来源的 tok/s 数字不应横向引用。** 若做选型，必须在自己目标机型 + 自己目标量化位宽 + 自己真实 prompt 长度上重测。

**更新三：框架差异在 NPU 上被极度放大，生态碎片化是真实成本。**

同一后端（Qualcomm QNN）、同一模型，GENIE / MNN / llama.cpp 三者的 prefill 吞吐差 15 倍 [S6]。且 MNN 把 self-attention 留在 CPU、引入 RPC 与内存布局转换，NPU 插件占端到端延迟 98.94% [S6]。MLC-LLM 则完全没有 NPU 后端。

另有移动端多实例测量显示：并发场景下 MNN 吞吐退化 55%，llama.cpp 只退化 17% [S37]。**框架选型不是实现细节，是架构决策。**

## 二、核心发现

### 发现 1：端侧小模型的能力边界不是"弱"，而是"窄且不对称"

在**封闭标签空间、单轮、短输出**的任务上，1.5B–3B 模型的表现接近甚至超过更大模型；在**开放生成、多轮、长程状态**的任务上则断崖式下跌。这个不对称性决定了整个分工设计。

以函数调用为例（BFCL，2026-02 快照）[S22][S23]：

| 模型 | 规模 | BFCL Non-Live | BFCL Live | BFCL Exec |
|---|---|---|---|---|
| Qwen2.5-1.5B | 1.5B | 86.3 | 67.4 | 91.9 |
| Qwen2.5-3B | 3B | 92.5 | 73.0 | 86.6 |
| Qwen3-4B | 4B | 93.7 | 77.9 | 94.6 |
| Qwen2.5-14B | 14B | 94.0 | 76.6 | 94.0 |

**单轮函数调用上，1.5B 与 14B 的差距只有 8 分左右，3B 已经基本追平。**

但同一批模型在 BFCL 的复杂分项上崩塌 [S23]：Qwen2.5-1.5B 的 Multiple 分项 0.50、Parallel-Multiple 0.458；Qwen2.5-3B 的 Parallel-Multiple 只有 0.458。多轮场景更差——FunReason-MT 报告 Qwen3-4B base 的 BFCL-V3 Multi-Turn Overall 仅 **15.75** [S23]。

**专用小模型可以显著优于通用大模型**：xLAM-1B-fc-r（1.3B）BFCL 69.67、Hammer2.1-3B（3B）BFCL 81.42 / ToolAlpaca 80.31，后者已超过 GRANITE-20B（72.83）[S23]。**为单一任务微调的 1–3B 模型，在这一任务上可以打赢 20B 通用模型。**

### 发现 2：路由的收益是条件性的，且路由不能创造能力

这是本次调研中最重要的两条负面证据。

**证据 A —— 收益完全由工作负载难度决定。** RouteLLM（ICLR 2025）的成本节省在 MT-Bench 上是 85%、MMLU 45%、GSM8K 35%，保留 95% 前沿模型质量 [S11]。同一框架、同一方法，节省幅度从 85% 滑到 35%，唯一变量是"这个负载里有多少题是简单题"。开放闲聊类负载 14–26% 走强模型即可，知识考试类需 54% [S11]。

**证据 B —— 路由能做到"少用云"，但做不到"质量对齐"。** SWARM-LLM（2026-06）在 50 题负载（20 易 / 20 难 / 10 安全）上的完整对比 [S7]：

| 架构 | 均值延迟(s) | P95 延迟(s) | 云使用率 | 总准确率 | 易题 | 难题 |
|---|---|---|---|---|---|---|
| Edge-Only | 1.05 | 2.28 | 0% | 0.225 | 0.45 | **0.00** |
| Cloud-Only | 4.47 | 11.33 | 100% | 0.475 | 0.65 | **0.30** |
| SWARM-LLM | 5.08 | 13.18 | 28% | 0.250 | 0.35 | 0.15 |

云使用率压到 28%（边缘处理 72%），云数据暴露率降 72%——**但难题准确率只有 0.15，纯云是 0.30，差距没有被任何共识机制闭合。** 更关键：SWARM-LLM 的均值延迟（5.08 s）**高于**纯云（4.47 s），因为它采用"先本地再升级"的级联顺序 [S7]。

**三条可操作的推论**：
1. 采用级联（cascade）路由，在延迟敏感的交互路径上会**恶化**体验而不是改善。
2. 若目标是"断网不停服"，那么必须接受"断网期间能力显著下降"，并把这件事在产品层说清楚，而不是靠路由算法弥补。
3. 路由的价值主要落在**成本与隐私**，而不是**质量**。

### 发现 3：更好的路由设计是"预测式 + 预算感知 + 子任务粒度"

HybridFlow（arXiv:2512.22137，v5 2026-08）给出了目前最完整的工程化方案 [S8]：

- **端侧**：Llama3.2-3B（同时充当 Planner 和 Edge Executor）；**云端**：GPT-4.1
- **粒度**：不是按 query 路由，而是把 query 拆成依赖感知的 DAG，**按子任务**路由，新解锁的子任务并行执行
- **判据**：轻量两层 MLP，输入 = 子任务语义嵌入（用 Qwen3-Embedding-0.6B 编码）+ 实时累积归一化成本；离线用 profiling 得到的准确率增益与成本构造目标效用 `u = clip(Δq/(c+ε), 0, 1)`，MSE 损失 + AdamW（lr 1e-4）warm-start；在线用上下文老虎机（LinUCB）做校准
- **结果**：

| 方法 | 卸载率 | 准确率 | 延迟(s) | API 成本($) | 效用 |
|---|---|---|---|---|---|
| Edge (L3B) | 0% | 25.54 | 11.99 | 0 | — |
| Cloud (G4.1) | 100% | 57.28 | 18.26 | 0.0185 | 0.4090 |
| Random | 42.1% | 46.00 | 15.15 | 0.0075 | 0.5922 |
| 固定阈值 | 41.18% | 51.62 | 15.88 | 0.0088 | 0.6292 |
| **HybridFlow** | **40.48%** | **53.33** | **15.24** | **0.0075** | **0.7940** |

（GPQA 消融表）[S8]。跨四个基准（GPQA 53.33 / MMLU-Pro 72.54 / AIME24 36.67 / LiveBench-Reasoning 58.83，均值 55.34），平均延迟 17.48 s、API 成本 0.0088 美元，相对 HybridLLM 延迟降 28.5%、成本降 31.3% [S8]。

**与固定阈值对比最能说明问题**：相同卸载率（40.48% vs 41.18%），HybridFlow 准确率高 1.71 分、延迟低 0.64 s、成本低 15%。**路由判据的质量，而不是路由的比例，决定了收益。**

另一条路线值得关注（arXiv:2509.24050，v4 2026-05）：不再外挂路由器，而是**用强化学习后训练让端侧模型自己决定是否请求云端**，采用分层奖励 + group-level policy gradient + 自适应 prompt 过滤，专门防止"永远本地"或"永远上云"的策略崩塌 [S9]。这是从"外部路由"到"内生路由"的范式转向，但目前缺少端侧部署的开销实测。

### 发现 4：人格连续性在长程交互中系统性衰减，且与模型规模不完全线性

这是对"断网时如何维持人格连续感"这个问题最重要的一组证据，且结论是负面的。

**Anchor 审计框架（Salesforce AI Research，arXiv:2607.28818，2026）**[S12]：

- 实验规模：**2,008 段对话** × 27 个 persona × 9 种交互调度 × 3 种记忆设置 × 4 个模型（Claude Sonnet 4.6 / Gemini 2.5 Pro / GPT-4o-mini / GPT-5-mini），每段 85–130 个 session
- **Trajectory accuracy（轨迹回忆）平均仅 44.4%**，四选一随机基准为 25%
- **User-state recall 始终在 0.214–0.250**，即**完全等同于随机猜测**
- Questionnaire retention（102 项密封问卷）：Gemini 2.5 Pro 0.810 > Claude Sonnet 4.6 0.764 > GPT-4o-mini 0.610 > GPT-5-mini 0.595
- **三种记忆实现（long-context / hierarchical summary / self-managed JSON）无一能稳定解决轨迹失败**（聚合准确率 0.430 / 0.441 / 0.459，差异不显著）
- 论文明确结论："**当前无任何被评估的模型或配置能在长期陪伴中可靠保持人格扮演或轨迹记忆**"

**Persistent Personas（arXiv:2512.12775）**[S13] 给出了机制层面的解释：超过 100 轮对话后，persona 特有的 token 模式频率**下降超过 40%**，而基线助手模式的 token 频率上升。这是**系统性的回归到训练默认行为**，不是随机质量损失。系统提示被对话历史"淹没"。论文同时测试了 Gemma 4B vs 27B、Qwen 4B vs 30B——**扩大规模可以缓解但不能消除**。

**Stable Personas（arXiv:2601.22812，CHI 2026）**[S14] 补充了一个关键的不对称性：**模型的自评人格特征在会话内和会话间都高度稳定，但观察者评定的 persona 表达随对话进行而下降。** 即模型"以为自己还是那个角色"，但外部行为已经漂移——这本质是身份层的谄媚（sycophancy）。

**对架构的直接含义**：把人格靠"会话开头一段 system prompt"来维持，在长程交互中必然失败。需要的是**每次会话都重新注入的结构化身份状态**，而不是一次性描述。

### 发现 5：断网降级是一个必须"设计过"的状态，而不是异常分支

工程界已形成较成熟的方法论，核心是**用能力对象（capability）路由，而不是用连通性（connectivity）路由** [S35]：

```
Capability = {
  local: "ready" | "loading" | "unsupported",
  remote: "reachable" | "unreachable" | "unauthorised",
  metered: boolean,
  batteryLow: boolean
}
```

关键点：`remote` 只有在**最近一次请求真正成功过**之后才标记为 reachable，而不是读接口标志位。失败请求应当作为证据，触发短窗口熔断——这正是标准的 circuit breaker 模式 [S35]。

据此把请求分四类，每类的降级行为在设计期就固定下来 [S35]：

| 类别 | 定义 | 在线时 | 离线时 |
|---|---|---|---|
| local-sufficient | 端侧答案真的够用（分类、抽取、改写、本地检索） | **也走本地**（省延迟、省钱、省隐私） | 本地 |
| degradable | 云端更好但本地可用（摘要、建议、草稿） | 优先云端 | 本地 + **标注** + 联网后询问是否重做 |
| deferrable | 只有云端能做且不急于此刻（长文档分析、批处理） | 云端 | **入持久队列**，告知用户已排队 |
| refuse | 既不可降级也不可延后 | 云端 | **明确、即时、不归咎用户**的说明 |

第四类必须被显式命名，因为它的错误处理方式正是"报网络错误"——而正确做法不是拿本地模型的劣质输出伪装成同一个答案 [S35]。

**队列的工程约束**（这部分决定了断网体验的可靠性）[S35][S36]：
- 持久化**请求**而非闭包；内存中的回调无法在进程被杀后存活
- 每个请求带**幂等键**（enqueue 时生成一次 UUID，重试复用），避免模糊超时后产生第二次计费或重复副作用
- 发送前校验目标对象（文档/消息/设置）仍然存在且未变更

## 三、关键数据与案例

### 3.1 端侧隐私守门：这一环证据最充分，可直接落地

**这是整个端侧分工里最扎实的一环**——因为任务本身是封闭标签空间的分类，恰好落在小模型的强项区。

**SecureOutbox（TechRxiv，2026）**[S17]：7 个量化 SLM（Llama-3.2 1B/3B、Gemma-2 2B、Gemma-3 1B、Phi-4-Mini、Qwen3 1.7B/4B）× 两套数据集共 41,000 样本，做全端侧 DLP（数据外泄防护）。

| 数据集 | 样本量 | 表现 |
|---|---|---|
| PHI（医疗信息） | 1,000 | Qwen3-4B **F1 0.975**（格式合规 100%）；Gemma-2-2B F1 0.962；Llama-3.2-3B F1 0.952 |
| PII（个人信息） | 40,000 | Gemma-3-1B **F1 0.999**；Llama-3.2-3B F1 0.974 |

**Llama-3.2-3B 是跨任务最一致的选择**（PHI 0.952 / PII 0.974，格式合规 0.956）[S17]。论文同时给出可运行原型：Node.js + React + Vite 浏览器扩展，用 WebGPU（WebLLM）全端侧运行，并强调**必须加确定性回退逻辑以降低 false-SAFE 率**。

**OpenAI Privacy Filter（2025）**[S21]：1.5B 总参数 / **50M 活跃参数**，span-decoding 双向 token 分类器（非自回归逐 token 生成，单次前向完成标注 + 受限 Viterbi 解码），128K 上下文，输出 8 类标签（private_person / private_address / private_email / private_phone / private_url / private_date / account_number / secret），**体积足够小以支持本地运行**。这是厂商官方产品，代表了"端侧 PII 过滤"的商业化标杆。

**安全围栏也是端侧强项**：

| 方案 | 模型规模 | 关键指标 | 来源 |
|---|---|---|---|
| LiteLMGuard | ELECTRA **15M** | 97.75% answerability 分类准确率；>85% 有害 prompt 防御率；94% 过滤准确率；**~135 ms** 延迟 | [S18] |
| Reflex-Guard | 句子向量 + 7 个二分类器 | 30,568 样本上 **95.9% recall @ 37.6 ms**；Llama Guard 2 为 255 ms、SafeDecoding 723 ms；100% 检出 GCG suffix 与 Base64 攻击 | [S19] |

LiteLMGuard 的关键论点是：**量化本身会引入安全退化**——量化后的 SLM 会不经任何对抗操纵就直接回答有害问题 [S18]。而 15M 参数的 guard 模型能达到甚至超过 7B+ 的 Llama Guard 2/3 与 ShieldGemma，"性能接近，模型小 100 倍以上"[S18]。

**但必须记录一个严厉的负面案例。** edge-guard（DeBERTa-v3-xsmall，70.8M）在其模型卡上主动披露 [S20]：
- 随机划分下 PR-AUC 0.999，但 **grouped-by-source 交叉验证（OOD）掉到 0.932 ± 0.067，最难 fold 仅 16.0%**——前一个数字是跨源记忆造成的虚高
- 在 433 条含"ignore / pretend / system"触发词的**良性** prompt 上，1%-FPR 工作点的**假阳性率高达 35.1%**
- 作者自述："**过度防御，而不是漏检，才是部署阻塞问题**"，并明确标注"Do not deploy this as-is"

这条信息应当被严肃对待：端侧守门模型的最大风险不是漏拦，而是**误拦**——在陪伴类产品里，误拦会直接伤害体验和信任。

### 3.2 端侧感知过滤：分类能力可用，但泛化是硬伤

| 方案 | 任务 | 规模/资源 | 表现 | 来源 |
|---|---|---|---|---|
| 轻量 SER（bio-inspired） | 语音情绪 | RPi 4 / 中端 Android | EMO-DB/RAVDESS/TESS 上准确率 >90%，UAR >88%；**延迟 <150 ms**，端到端 <500 ms | [S33] |
| TinyML SER | 语音情绪 | TFLite 量化，体积降 94.5% | 74.15% 准确率，macro F1 0.73；**推理延迟 3.4 ms** | [S33] |
| Edge TPU 多模态情感 | 声学 + 文本晚期融合 | **1.8 MB 内存预算** | 21–23 ms 延迟；macro F1 比单模态 **+6.3%** | [S34] |

**读数要注意**：这些是受控情感数据集（RAVDESS/TESS/SAVEE/IEMOCAP）上的数字，论文本身承认"单语言或单口音数据集导致对多样说话人、口音和真实世界的推断无效"[S33]。**端侧做"情绪强度/唤醒度粗分类"可行，做"情绪语义理解"不可行。**

### 3.3 打扰度打分：文献给出了明确的否定性结论

这是本调研中被点名要求评估的功能，而结论是：**"打扰度"不是一个可靠的监督目标。**

**证据 A —— 多模态 LLM 检测可打断性未达预期。** AHs '26（ACM，2026-05）的 N=21 用户研究在办公场景用 LLM 综合视觉信息与交互参数调度通知 [S16]。三条结果：
- 系统"未能完全达到设计潜力"，因为可打断性是**动态且高度个体化因素的交织**
- **提供用户历史评分记录带来最大改进**
- **移除所有上下文特征反而得到最好的整体对齐**

论文结论："这凸显了自我报告可打断性的强时间效应，并**提示单纯多模态推断的局限**"[S16]。

**证据 B —— 干预时机本身是低可靠性构念。** arXiv:2606.04296（2026-06）在 SWE-bench-Verified 调试轨迹上评测四类干预触发器 [S15]：
- **State Saturation Trap**：智能体在持续困难下不显示恢复信号，建模的挫败感迅速触顶并保持最大，使"阈值触发"从时刻检测器变成**近乎恒定指示器，在五条轨迹上于 39–83% 的动作上触发**
- **LLM judge 的能力-上下文地板**：小模型（gpt-5.4-mini）**从不触发**；前沿模型仅在拿到全轨迹上下文时才能脱离"零触发地板"，且 F1 仅 **0.17–0.40，成本最高达 90 倍**
- **监督目标在人类之间不可复现**：三名受训标注者用同一评分标准标注一条 56 动作轨迹，在"该在哪里干预"上仅**略高于随机**（位置 Krippendorff's α = +0.047，最佳成对 Cohen's κ = +0.349），在"干预类型"上完全不一致

论文明确结论："干预时机是一个低可靠性构念，使单标注者 F1 成为不合适的优化目标"[S15]。

**架构含义**：把"打扰度打分"作为端侧模块设计时，不要把它当作一个可优化的分类器精度问题。可行的替代是**把打扰度降级为规则 + 用户显式偏好 + 历史评分的混合策略**（对应证据 A 中唯一有效的改进方向），并保留用户随时改写的权利。

### 3.4 记忆与巩固：断网期是"睡眠"窗口而非停机窗口

**Sleep-time Compute（Letta + UC Berkeley，arXiv:2504.13171）**[S24]：让模型在查询到来**之前**离线"思考"——预测用户可能问什么并预计算。结果：达到同等准确率所需测试时算力**降低约 5 倍**；扩大睡眠算力可再提升准确率最多 **+13%**（Stateful GSM-Symbolic）/ **+18%**（Stateful AIME）；对同一上下文的多个相关查询摊销后**平均单查询成本降 2.5 倍**。论文特别指出：**用户查询的可预测性与睡眠计算的效果高度相关**。

**Language Models Need Sleep（arXiv:2605.26099，2026-05）**[S25]：当上下文窗口填满时，模型进入睡眠阶段——对累积上下文做 N 次循环离线遍历，把信息写入状态空间模块（SSM）内的 fast weights，然后清空 attention cache。**睡眠越长（N 越大）性能越好，且增益主要集中在需要深度推理的难题上**。唤醒后的预测仍是单次前向，延迟不变。

**SCM（arXiv:2604.20943，2026-04）**[S26]：更接近产品化的记忆架构，包含五个组件——有限容量工作记忆、四维重要性标记（新颖性/情绪效价/任务相关性/重复频率）、**NREM + REM 双阶段离线睡眠巩固**、基于价值的主动遗忘、计算自我模型。在八项测试的标准套件上达到十轮对话**完美召回**，通过自适应遗忘**降低记忆噪声 90.9%**，记忆搜索延迟在数百个概念规模下**低于 1 毫秒**。

**架构含义**：对于一个断网会周期性发生的伴生 Agent，断网不应被处理为"功能降级期"，而应被处理为**记忆巩固窗口**——离线做上下文压缩、重要性标记、主动遗忘。联网恢复后同步的是**巩固后的状态**，而不是原始对话回放。

### 3.5 端侧检索：已完全可行，且成本很低

| 模型 | 参数 | 维度/上下文 | MTEB | 体积 | 来源 |
|---|---|---|---|---|---|
| EmbeddingGemma | 308M | 768 (MRL 可截断至 128) / 2048 | <500M 类别开源多语最优 | 量化后 **<200 MB RAM**；EdgeTPU 上 <15 ms（短输入） | [S30] |
| Qwen3-Embedding-0.6B | 0.6B | 32–1024 (MRL) / 32K | 英文 v2 **70.7**；多语 64.64；C-MTEB 71.02 | Q4 GGUF ~400 MB | [S30] |
| all-MiniLM-L6-v2 | 22.7M | 384 / 256 | 56.26（MTEB eng） | 0.1 GB | [S30] |

**int8 动态量化可减体积约 75%，精度损失仅 1–3%** [S30]。端侧 RAG 的完整链路（本地 embedding + 本地向量库 + 本地 3B 生成）在 2026 年已无技术障碍，主要风险转移到 embedding 与 LLM 之间的语义空间不匹配。

### 3.6 量化：对小模型的伤害不成比例

一个普遍被低估的坑。GPTQ 原始论文（ICLR 2023）的 OPT 族困惑度表 [S32]（GPTQ 4-bit 相对 FP16 的变化）：

| 规模 | 125M | 1.3B | 2.7B | 6.7B | 13B | 30B | 175B |
|---|---|---|---|---|---|---|---|
| 相对困惑度变化 | **+12.5%** | +5.7% | +3.2% | +4.9% | +1.8% | +0.7% | +0.4% |

**小模型的权重冗余更少，量化损失更不成比例。** 1B 模型的 int4 量化常产生 5–15% 的退化，而非 7B+ 模型的 <1% [S31]。

更直接的端侧证据：arXiv:2607.05475 实测 W4A16（4-bit 权重 + 16-bit 激活）虽然能将 NPU 能效提升 2 倍以上，**但让 Llama3.2-1B 的困惑度恶化 30.36%**，论文自述"未给出通用的精度-能耗权衡方案"[S6]。

**部署建议**：如果 1–3B 模型在 FP16 下能装进目标设备内存，就不要量化。量化应作为内存约束下的最后手段，而非默认选项。

### 4.2 本调研的局限性（诚实声明）

1. **多数端侧性能数据来自实验室短序列。** arXiv:2607.05475 固定 256-token 负载，**未覆盖真实移动 Agent 长时多轮工具调用、多实例并发等动态场景**，其调度建议需在实境再验证 [S6]。
2. **路由论文的负载规模有限。** SWARM-LLM 仅 50 题、且为单机模拟 swarm（不含真实无线争用与多跳延迟）[S7]；HybridFlow 的云端用 GPT-4.1，端侧 Llama3.2-3B，是**单点配置**，不外推到其他模型组合 [S8]。
3. **人格审计为全合成。** Anchor 使用英语、作者模板生成，无真实用户、无未成年人、无非英语交互；身份用西方心理量表操作化；用户轮次、评判、出题、校准均用 LLM，**评判者选择显著改变 role/style 结果** [S12]。
4. **打扰度结论基于特定域。** State Saturation Trap 的结论来自软件调试轨迹（SWE-bench）[S15]，AHs '26 来自办公场景 [S16]。陪伴类场景的交互节奏不同，直接迁移需谨慎。
5. **部分来源为二手转述。** 骁龙 3B 220 tok/s 为媒体转述厂商发布会 [S27]，未获官方技术白皮书原文；中文渠道的部分吞吐数据（如"20 tok/s"）来自券商研究报告整理，**未在本报告中作为关键论据使用**。
6. **未覆盖的方向**：端侧多模态（视觉/音频联合推理）的真实延迟预算；NPU 驱动层与系统调度对长时运行的影响；端云之间的模型版本漂移与蒸馏回路的灾难性遗忘（SWARM-LLM 已将其列为局限）[S7]。

### 4.3 需要明确标注的不确定信息

- **Gemma 2 2B 的 MMLU 得分存在三个互相冲突的数字**：技术报告口径 52.2 [S3]、中文媒体报道 56.1、另有渠道给出 42.3（该数字疑为 Gemma 1 2B 的口径）。**本报告采信技术报告口径 52.2，但标注存疑。**
- **MNN 与 llama.cpp 的 CPU 吞吐对比存在数量级冲突**：有测量显示 OnePlus 12 上 MNN CPU 25.70 tok/s 而 llama.cpp 仅 3.29 tok/s（Llama3.2-1B 4-bit）[S37]；而 arXiv:2607.05475 在骁龙平台上 llama.cpp CPU decode 达 51.6–76.1 tok/s [S6]。**两者测量条件（量化、后端、上下文、线程配置）显然不同，本报告不采信任一绝对值为跨平台结论。**
- **端侧模型的"拟态动作"能力（短回应、表情、节奏控制）缺乏直接文献支持。** 本报告的讨论基于"封闭标签空间分类"的类比推断，属于工程判断而非有实证的结论，**已在建议章节明确标记**。

## 五、结论与建议

### 5.1 三个必答问题的直接回答

---

**问题一：端侧 1.5B–3B 能可靠承担哪些任务，哪些不能？**

**✅ 可可靠承担（有实证支持，建议无条件本地化）**

| 任务 | 支持证据 | 建议模型档位 |

| PII/PHI 检测与脱敏 | F1 0.95–0.999（1B–4B）[S17]；OpenAI Privacy Filter 1.5B/50M 活跃 [S21] | 1B–3B 或专用 300M |

| 任务 | 反证 |
|---|---|

| **长程记忆与状态回忆** | 云端强模型在 Anchor 上也仅 44.4% 轨迹准确率、近随机的用户状态回忆 [S12]，端侧只会更差 |

---

**问题二：端云路由判据如何设计？**

**第一条原则：用 capability 对象路由，不用连通性路由。** 网卡标志位会说谎（captive portal、已连但不可达、可达但不应发），`remote` 状态必须由**最近一次真实请求的成功**来维护 [S35]。

**第二条原则：预测式优先于级联式。** 级联（先本地，不满意再升级）会让延迟**变差**——SWARM-LLM 实测 5.08 s vs 纯云 4.47 s [S7]。对延迟敏感路径必须用"生成前决策"（RouteLLM 式）[S11] 或"子任务 DAG + 效用模型"（HybridFlow 式）[S8]。

**第三条原则：判据分层，成本递增，越往下越不划算。**

| 层级 | 判据 | 成本 | 证据 |
|---|---|---|---|
| L0 | 请求类别（设计期静态分类）+ capability 状态 | 零 | [S35] |
| L1 | 端侧不确定性信号：归一化序列熵 `H = -1/N Σ P log P` + logit 方差 `V = 1/N Σ Var(z_top-k)`，组合为 `U = αH + (1-α)V̂` | 极低（复用本地生成） | SWARM-LLM 用法 [S7] |
| L2 | 语义嵌入 + 轻量 MLP 打分（HybridFlow：Qwen3-Embedding-0.6B + 2 层 MLP  + 累积成本特征） | 低（一次 embedding + MLP 前向） | [S8] |
| L3 | 端侧模型自评 / 自一致性多采样 | 中（牺牲延迟） | — |
| L4 | 云端 LLM-as-judge | **高，不推荐** | F1 0.17–0.40 且成本 90× [S15] |

**第四条原则：预算感知，而非静态阈值。** HybridFlow 用 `u = clip(Δq/(c+ε), 0, 1)` 作为效用目标（Δq 为准确率增益，c 为归一化成本），配合在线 LinUCB 校准 [S8]。消融显示：**相同卸载率下（40.48% vs 41.18%），效用 0.7940 vs 0.6292，准确率高 1.71 分、延迟低 0.64 s、成本低 15%** [S8]。这说明"判据的质量"而不是"路由的比例"才是收益来源。

**第五条原则：隐私/安全风险独立成路，不走效用优化。** 高风险请求（涉敏感数据、越狱特征）直接走本地安全路径或本地拒绝，**不进入"要不要上云"的成本收益计算** [S7 的 O4 目标]。

**必须同时接受的现实**：路由不能创造能力。若产品承诺是"任何时候都一样好"，那么任何路由方案都会让这个承诺失效。正确做法是把"什么时候会变差"显式地告诉用户（见问题三）。

---

**问题三：断网时如何维持人格连续感，而不是报网络错误？**

把这个问题拆成三层，每层都有对应的可执行手段。

**第一层：不要让人格靠 prompt 维持。**

Anchor 的实测已经证明这是失败的路径——三种记忆实现（long-context / 分层摘要 / 自管理 JSON）都无法稳定解决轨迹失败 [S12]，且人格崩塌在**第一次 checkpoint 之后就出现** [S12]。

可行的替代是**把人格从"一段描述"转成"一组可重放的结构化状态"**：
- 身份轴拆分为可独立校验的维度（角色 / 边界 / 价值观 / 风格），对应 Anchor 的 Identity Probe 设计 [S12]
- **每次会话开始时重新注入**，而不是会话开头注入一次（对应 Persistent Personas 发现的"系统提示被对话历史淹没"机制 [S13]）
- 关键承诺与状态变更**单独持久化**，并在相关轮次强制重放（Anchor 显示 active commitment 准确率仅 0.337–0.446，是最弱项之一 [S12]）

**第二层：把"断网"从异常状态改写为产品状态。**

这是维持连续感的关键动作——**断网必须表现为"角色的当下状态"，而不是"系统的故障"**。

| 反模式 | 替代设计 |
|---|---|
| "网络异常，请检查连接" | 角色以自身能力边界作陈述，把限制纳入人格叙事 |
| 用端侧劣质输出冒充云端答案 | 明确标注这是本地回应，联网后询问是否重做 [S35] |
| 静默等待/无限 loading | 明确告知：**现在能做什么**、**什么已排队**、**何时会补上** [S35] |
| 重复重试死端点 | 熔断 + backoff，`remote` 状态由真实成功维护 [S35] |

配套的工程支撑：请求持久化（存输入不存闭包）、幂等键防重复副作用、发送前校验目标对象未变更 [S35][S36]。

**第三层：把断网窗口变成记忆巩固窗口。**

Sleep-time Compute 证明离线预计算可达 **~5× 测试时算力节省**，且用户查询可预测性与收益高度相关 [S24]——而伴生 Agent 的查询恰恰是**高度可预测**的（问候、情绪确认、日程询问）。Language Models Need Sleep 证明离线巩固可以把上下文压进固定大小的状态，**唤醒后仍是单次前向，延迟不变** [S25]。SCM 给出了接近产品化的实现，**记忆噪声降 90.9%、搜索延迟 <1 ms** [S26]。

具体做法：断网期执行 NREM 式重要性标记与压缩 + 主动遗忘；联网恢复后同步**巩固后的状态**而非原始对话回放。

**第四层：把"打断"这件事从算法问题降级为交互问题。**

打扰度打分作为端侧智能模块在文献上不成立（见 3.3）[S15][S16]。可行的替代路径是证据 A 中唯一有效的改进方向——**用用户历史评分**，辅以显式偏好设置，并保留用户随时改写的权利 [S16]。

**关于"拟态动作"的坦率说明**：本报告未找到端侧模型执行拟态动作（回应节奏、表情、微交互）性能的直接文献。从"封闭标签空间分类"的类比推断，端侧做**短回应模板选择与节奏控制**是可行的（与意图分类同构），但**这是工程判断，不是有实证支持的结论**。建议的做法是：把拟态动作实现为**确定性的状态机 + 本地模板库**，而不是交给端侧 LLM 生成——这样既避免了小模型的生成不稳定，也保证了断网时的一致性。

### 5.2 建议的目标架构（三级能力栈）

| 层级 | 位置 | 承担 | 延迟预算 | 断网时 |
|---|---|---|---|---|
| L0 反射层 | 端侧，15M–300M 专用模型 + 规则 | 安全围栏、PII 脱敏、VAD、唤醒词、意图分类、embedding 检索 | <50 ms | 完整可用 |
| L1 守门层 | 端侧，1.5B–3B（W8/FP16 优先） | 路由决策、简单生成、单轮工具调用、离线兜底对话、拟态动作状态机 | 1–3 s | 完整可用（能力受限） |
| L2 认知层 | 云端，前沿模型 | 复杂规划、深度共情、记忆巩固、长程状态维护、多轮工具调用 | 不限（可异步） | 降级 + 排队 |
| 旁路 | 端侧，常驻后台 | 断网期记忆巩固（睡眠计算）、恢复后状态同步 | 离线 | — |

### 5.3 落地优先级（按证据强度排序）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | 端侧 PII/敏感信息脱敏层 | 证据最充分（F1 0.95–0.999）[S17][S21]，收益明确（隐私），无能力风险 |
| **P0** | capability 对象 + 四类请求分类 + 持久队列 + 幂等键 | 纯工程，无模型风险；直接决定断网体验 [S35] |
| **P0** | 端侧检索（EmbeddingGemma 308M 或 Qwen3-Embedding-0.6B） | 技术成熟、成本低 [S30] |
| **P1** | 身份状态结构化 + 每会话重新注入 | 针对性修复 Anchor 揭示的失败模式 [S12][S13] |
| **P1** | 断网期记忆巩固（睡眠计算） | 有实证收益（~5× 算力节省）[S24][S25][S26] |
| **P1** | 单轮函数调用的端侧化（明确排除多轮） | BFCL 单轮证据充分 [S22][S23]；多轮明确不可行 |
| **P2** | 语义嵌入 + MLP 式的预算感知路由器 | 需要标注数据与 profiling，收益确定但建设成本高 [S8] |
| **P3** | 打扰度模型 | **建议先不做**。文献不支持把可打断性作为可优化目标 [S15][S16] |
| **P3** | 端侧多轮工具调用 | 文献明确不支持 [S23]，等待下一代 |

### 5.4 明确不要做的事（负面清单）

1. **不要用"联网/断网"做路由判据。** 用 capability 对象 [S35]。
2. **不要在延迟敏感路径上用级联路由。** 它会增加延迟 [S7]。
3. **不要把 NPU 当默认最优后端。** decode 阶段 CPU 常更快、更省电 [S6]。先做 phase-aware 测。
4. **不要在 1–3B 模型上默认 int4。** 若 FP16 装得下就别量化 [S31][S32]；W4A16 让 1B 模型困惑度恶化 30% [S6]。
5. **不要把端侧 guard 模型当唯一防线。** 必须有 OOD 测试与云端复核路径 [S20][S18]。
6. **不要用云端 LLM-as-judge 做实时路由判据。** F1 0.17–0.40 且成本 90× [S15]。
7. **不要承诺"断网时一样好"。** 数据不支持。承诺"断网时仍然是她，但这次只能聊她记得的事"。
8. **不要只看厂商基准做选型。** 必须自测：目标机型 + 目标量化 + 目标 prompt 长度 [S6][S27]。
