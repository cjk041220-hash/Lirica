## 一、外部报告逐条核对

| # | 外部报告论断 | 核对结论 | 证据与说明 |
|---|---|---|---|
| 1 | `appScope` 用 `Dispatchers.Default` 是 P0 | ⚠️ **属实但定级过高**（实为 P2） | `XiaoxiApplication.kt:54` 确为 Default。但 appScope 驱动的 collect 以 StateFlow 复制为主（CPU 轻量），Room suspend 调用内部自带 IO 调度，Ktor 在自己的引擎线程上跑。改 `Dispatchers.IO` 是合理微调（1 行），但**当前没有证据表明存在线程竞争或响应延迟**。"P0" 不成立 |
| 2 | 15 个 `lateinit var` + 同步 onCreate → ANR 风险 | ⚠️ **属实但严重性夸大**（实为 P2 中期重构） | 15 个 `lateinit` 数目正确（XiaoxiApplication.kt:56-99）。但全部是轻量构造器调用，`Room.databaseBuilder().build()` 不做磁盘 IO（首次查询才开库），`PerceptionPipeline.start()` 是非阻塞 launch——**冷启动无 ANR 之虞**。DI 化是长期收益项，不是止血项 |
| 3 | release 未启用混淆 | ✅ **完全正确** | `build.gradle.kts:40` `isMinifyEnabled = false`；proguard-rules.pro 已备好未启用；且 PROGRESS_TRACKER.md:20 声称"R8 已全绿验收"——文档失实。与砚复检严重#3 重合 |
| 4 | `versionCode = 1` 与 `versionName = "2.0.0"` 不一致 | ⚠️ **事实对，但对本项目无影响**（P3） | 单用户侧载项目、无应用商店分发，versionCode 仅要求递增即可。报告自己也承认"全新项目从 1 开始没有问题"。可不修 |
| 5 | AccessibilityService `exported="true"` 是安全风险，建议改 false | ❌ **错误且有害，不要采纳** | `AndroidManifest.xml:53-56`：该服务带 `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`——**只有系统进程能绑定**，恶意应用无法利用；`exported="true"` 是无障碍服务被系统绑定的**必要条件**，改成 false 会导致无障碍功能直接失效。通知监听服务（:68-70）同理 |
| 6-7 | Java 21 / compileSdk 35 配置正确 | ✅ 双方一致 | 无分歧 |
| 8 | 无 PR/Issue 流程 | 中性 | 单人项目现状如此，CI/CD 属可选工程化项 |
| 9 | API Key fallback `"default-key"` 应改 `error()` | ⚠️ **合理建议**（P2，需权衡） | `build.gradle.kts:17` 属实。改 `error()` 会阻断未配 Key 的构建（如新 clone / CI）；单用户场景下直接报错更安全。真正的风险是**真 Key 编译期明文进 APK**（砚复检严重#3 已覆盖） |
| 10 | 整体评分与后续建议 | ⚠️ 方向可用 | 但"下一步优先级"第 1 条（appScope）收益很小，而真正致命的 5 个问题一条都没提到——**该报告深度不足，未做跨文件接线核对与 schema 对比** |

**对外部报告的总评**：静态扫描 + 局部阅读的水平，适合做"补充视角"，不适合作为修复依据。它的 R8、default-key 两条有价值；exported 一条照做会弄坏功能；appScope/lateinit 两条定级虚高制造焦虑。
