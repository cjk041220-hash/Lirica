# 小汐上线前体检清单 — 跨会话逐项推进设计文档

日期：2026-08-06
状态：已确认（设计 v2 三节，用户口头批准）

## 背景与目标

上线在即（公网服务器 + 域名），需要对小汐做全面体检。用户否定了「一次性全量体检」与「全量测试跑绿即算数」两条路径：

1. **全量测试不够细致准确**：pytest 是断言级验证，覆盖不到真实 LLM 行为、时序、部署链路、安全暴露面、资源占用；
2. **一次性体检浪费 AI 注意力**：单个会话 context 有限，200+ 检查项挤在一个窗口里，越往后越糊。用户将**多开几轮新窗口，每轮只检查局部**，最大效率利用 AI 的注意力。

工作模式（用户原话要点）：**虽看虽修，修完确认，然后下一项**——每项检查发现问题当场修复，修完复验确认，再进入下一项。

## 设计原则

1. **清单即进度档案**：进度不存会话记忆，全部以 checkbox 勾选 + 结果栏文本持久化在清单文件里，git 提交即存档。任何新窗口读文件即可续跑，不需要前文。
2. **板块文件自包含**：每板块一个文件，是独立执行单元。新窗口 AI 不需要任何前文，读一个文件就能干活。
3. **独立取证，不依赖测试路径**：每个检查项定义独立验证手段（真实实例 API 实测 / 直查 SQLite / 日志 / 文件 / 代码核验）。pytest 只作背景基线（当前 740 passed），不作为检查项的通过判据。
4. **真实实例低风险检查**：在常驻实例 :8000 上执行，真实 key 验证「活的行为」（真实 LLM 输出、心跳时序、推送）。只读/低风险为主；少量必要的写入检查（如发一条测试消息）允许，产生真实数据可接受，禁止未经用户确认的破坏性操作（删库、清数据）。

## 二、板块文件内部结构

### 2.1 头部状态块（新窗口接管点）

```markdown
# 07 · 安全与隐私体检

> 板块状态：7/25 通过 · 2 项发现问题已修 · 剩 15 项待检
> 已知问题：P1 #7.9 反代未开限流（修复摘要见结果栏）
> 续跑指引：从第一个未勾选项开始，每项「看→修→确认→勾选」；
>           修复涉及代码改动时，重跑相关 pytest 再勾选。
```

### 2.2 检查项五要素

```markdown
- [ ] **7.1 认证中间件覆盖全部 API**
      · 查：除 /api/health 外所有路由是否强制 Bearer token
      · 取证：curl 无 token 访问各端点 → 预期 401；核对 server.py 中间件注册
      · 判据：全部返回 401，无白名单遗漏
      · 严重度：P0
      · 结果：（通过勾选；❌ 时写发现+修复摘要+复验）
```

- **查**：这一项检什么（一句话）。
- **取证**：可执行的独立手段——curl 命令、sqlite 只读查询、日志路径、文件检查、代码核验点。必须具体到能直接执行，不得写「跑测试」。
- **判据**：什么算通过（可观测、可判定）。
- **严重度**：P0 阻塞放行 / P1 上线前修 / P2 可后置。
- **结果**：通过 → 勾选 checkbox；发现并修复 → 勾选 + 写摘要（问题、修法、复验证据）；无法当场修 → **保持未勾**，记入该板块「已知问题」与 00-summary 台账，标严重度（后续轮次或上线前决策处理）。

### 2.3 状态机

未检（`- [ ]`）→ 检查中 → 通过（`- [x]` + 结果 ✅）
                      └→ 问题已修（`- [x]` + 结果 ❌→ 摘要 + 复验 ✅）
                      └→ 遗留（`- [ ]` 保留未勾 + 记入已知问题台账，等待后续轮次或上线前决策）

## 四、总看板 00-summary.md

- 头部：执行纪律（见下）。
- 十板块进度条（如 `01 对话体验 ██████░░ 12/20 · 剩余 P0:0 P1:1`）。
- P0/P1/P2 问题台账：编号、板块、问题、状态（已修/遗留）、修复提交引用。
- 放行状态块：所有板块全勾 + 无未决 P0/P1 → 可上线；否则列出阻塞项。

## 五、执行纪律（写入 00-summary.md 头部，每轮新窗口都读到）

1. 每轮会话只开一个板块文件（至多两三个相邻项），保持注意力聚焦。
2. 从第一个未勾选项开始，顺序推进；每项「看 → 修 → 确认 → 勾选」。
3. 发现问题**当场修**：修复涉及代码改动时，重跑该功能相关 pytest + 复验该检查项的取证命令，确认后才勾选。
4. 每完成一批（或板块收尾）git 提交存档，commit message 注明板块编号（如 `feat(check): 07-security 通过 7.1-7.8`）。
5. 可随时中断：下次新窗口读 `00-summary.md` + 目标板块文件头部即续跑。
6. 禁止破坏性操作（删生产库/清数据）——确需时先问用户。
7. 新窗口接管协议：用户说「继续体检」→ 读 00-summary → 读目标板块文件 → 从第一个未勾项开始执行。

## 六、完成判据

- 十板块文件全部检查项勾选完成；
- 00-summary 台账无未决 P0/P1（P2 可注明延期原因）；
- 产出放行结论：✅ 可上线 / ⚠️ 有条件上线（列出条件）/ ❌ 阻塞。

## 七、与既有工作流的关系

- 本清单是 docs/ 下常驻的体检工作区（`docs/launch-check/`），不属于 superpowers spec/plan 生命周期；
- 执行中发现的结构性问题（非单点修复）若超出体检范围，记入台账并另开 spec/plan 处理，不在体检轮次里扩散。

## 八、交付物边界

- 本 spec 定义清单的**结构与纪律**；各板块 20-30 项检查项的具体内容（查/取证/判据/严重度）由实施计划逐板块产出，直接写入 `docs/launch-check/` 各板块文件；
- 实施阶段完成标志：11 个文件全部创建、检查项内容完备可执行、00-summary 看板与执行纪律就位——此后每一轮新窗口体检即可直接按清单执行，无需再设计检查项。
