# 一、结论摘要（TL;DR）

1. **方案的四条断层论断全部属实**，且均已逐条核实到 file:line 级证据（见第三节核验表）。方案对现状的诊断是可信的，五个子系统的大方向合理。
2. **方案的主要短板不是"写错了"，而是"漏了"**：作为"系统级全景方案"，它完全没有覆盖 **构建与发布配置、UI 渲染性能、稳定性监控、聊天主链路的上下文无界与双重召回浪费、API Key 与备份隐私缺口** 这五个工程面。这些恰好是"Phase 0~5 沙盒自洽 → 真实可日常运行"之间真正的拦路石。
3. **两处现状与方案认知不匹配**：① Function Calling 基建（SSE ToolCallChunk 解析 + ToolCallAssembler 分片聚合 + 请求 tools 字段）已是半成品，方案按"零基础"排期在 M2.4，应提前到 M2.2 就位；② 主对话上下文是**完全无界**的（比"Top-5 暴力拼接"更严重），Handoff 快照机制落地前需要一个廉价的硬预算兜底。
4. 建议在 M2.1~M2.4 之外**增补一条并行线 P 线（工程质量线）**，共 6 项，其中 3 项（R8/minify、上下文硬预算、崩溃捕获）应先于或伴随 M2.1 落地。

## 2.2 核心业务逻辑与数据流（当前真实接线状态）

```
感知四路信号（UsageStats 2s轮询 / 通知监听 / 无障碍轻量树 / 息屏）
   → PerceptionPipeline（汇总 + PrivacyBreaker 脱敏 + 驱动 EmotionEngine + 念头池投递）
   → [仅到情绪与念头为止；感知快照不进对话上下文]

聊天主链路 ChatViewModel.sendMessage (ui/chat/ChatViewModel.kt:98-284)：
   持久化用户消息 → recallUserMemories(5) ①第1次召回
   → assembleDynamicContext 内部再 recallUserMemories(5) ②第2次召回 (database/memory/DualTrackMemoryManager.kt:138)
   → PhiMiddleware.assemble（角色卡+世界书+动态记忆槽+历史+PHI 尾部重锚）
   → llmClient.streamChat（Ktor SSE，指数退避重试，network/XiaoxiLlmClient.kt:74-165）
   → 逐 token 更新 UIState → 完成后 HumannessFilter 自纠环 → 持久化 → MemoryExtractor 异步抽取

```

**未接线的"孤岛"**（与方案论断一致）：`automation/` 全部 16 个文件、`ProactiveBubbleCoordinatorImpl`、`BreakpointDetector`、`InterruptibilityEstimator` 在生产代码零实例化；`ToolCallAssembler` 与 `streamChat(tools=...)` 基建在位但无调用方；感知快照流从未被任何 UI/LLM 消费。

# 四、方案评审：缺失、不完整与不匹配项

## 4.A 【不匹配】Tool 基建已是半成品，方案按零基础排期
- **现状**：`network/model/LlmModels.kt:30-68,84`（ChatMessage 已含 tool_calls/tool_call_id，请求已含 tools 字段）、`network/ToolCallAssembler.kt:21-49`（分片聚合已实现且有单测）、`XiaoxiLlmClient.kt:127`（ToolCallChunk 已流入事件流）。
- **方案缺口**：Milestone 2.4 才"接入 Function Calling"，且表述为全新建设。
- **建议**：改表述为"补全 Tool 执行路由器与结果回传闭环"；基建部分可直接复用，M2.2 做 HelixGuiCoordinator 时即以 Tool Call 作为意图入口（`open_app/click/type` 声明工具），不必等悬浮 UI 完工。

## 4.B 【不匹配】主对话上下文完全无界，比方案描述更严重
- **现状**：`ChatViewModel.kt:181-189` 将内存中**全部**历史消息装配发送，无轮次上限、无 token 预算；会话过 50 轮后单次请求体积线性膨胀直至 400 错误。
- **方案缺口**：4.4.3 Handoff 快照机制只在"轮次>20 触发快照"的语境下提及裁剪，但 M2.3 才落地；**M2.3 之前没有任何兜底**。
- **建议**：在 M2.1 或更早加一个 20 行的硬预算截断（按字符数估算 token，保留 system+最近 N 轮），作为 Handoff 落地前的临时护栏，避免真机长会话直接打崩。

## 4.C 【缺失】聊天主链路双重记忆召回（方案未发现）
- **现状**：每条消息触发两次全量打分——`ChatViewModel.kt:134` 显式调用 `recallUserMemories(limit=5)`，`:158` 的 `assembleDynamicContext` 内部又调一次（`DualTrackMemoryManager.kt:138`），每次都对 200 条记忆做 bigram+6 因子打分（`DualTrackMemoryManager.kt:43`）。
- **影响**：CPU 浪费一倍；且两次召回结果无同步保证。
- **建议**：ChatViewModel 只调一次召回，结果复用传入 assemble；`assembleDynamicContext` 增加可选的预召回参数。
- **优先级**：高（改动 <20 行，纯收益）。

## 4.D 【缺失】UI 渲染维度整体空白
- **现状证据**：① 每 token 全量复制 messages 列表（`ChatViewModel.kt:211-216`，`map` 创建新 List）；② `ChatUiState.kt:12-19` `MemoryBadgeInfo` 含 3 个 `List<String>` 未标 `@Immutable` → `ChatMessageItem` 不稳定 → 流式期间所有可见 MessageItem 逐 token 重组；③ `ChatScreen.kt:59-63` 依赖 `lastOrNull()?.text`，每 token 触发一次 `animateScrollToItem`（动画 + 逐 token 重入 = 流式掉帧主因）。
- **建议**：① 流式文本独立成 `StateFlow<String>` 由 MessageItem 顶层单独 collect，或至少给列表更新换成"仅替换最后一条"；② `MemoryBadgeInfo` 加 `@Immutable`；③ 滚动改为 `scrollToItem`（非 animate）且仅在"用户已在底部"时触发。
- **优先级**：高。流式打字机是本产品最高频路径，对标"成熟商业产品水准"的交互目标下不能忍。

## 4.E 【缺失】构建与发布配置零覆盖
- **现状证据**：① `app/build.gradle.kts:40` release `isMinifyEnabled=false`，R8 与资源收缩全关，Ktor/OkHttp/kotlinx-serialization 全量进包；`proguard-rules.pro` 仅 3 行，开启 minify 后 kotlinx-serialization/Room 必须补 keep 规则；② `gradle.properties` 仅 4 行，无 `org.gradle.caching`、`org.gradle.parallel`、`org.gradle.configuration-cache`；③ 无 version catalog（13 处版本硬编码散落）；④ 无 Baseline Profile；⑤ 无 lint 配置。
- **影响**：APK 体积与冷启动无优化；构建速度未挖掘；版本升级靠手改。
- **建议**：见第五节 P1/P2/P3。
- **优先级**：中~高。

## 4.F 【缺失】API Key 与备份隐私缺口（与项目自我定位冲突）
- **现状证据**：① `app/build.gradle.kts:17,35` DEEPSEEK_API_KEY 烘进 BuildConfig，叠加 release 不混淆 → 可从 APK 静态提取；② `AndroidManifest.xml:32` `allowBackup="true"` 且无 `dataExtractionRules`（Android 12+）/`fullBackupContent` → 全部 Room 亲密记忆随云备份/设备迁移外流；③ `LlmConfig` 模型层支持 BYOK（`LlmModels.kt:18-28`）但**无任何设置 UI**，用户无法自备 Key，BYOK 目前只是模型定义。
- **建议**：① API Key 移出 BuildConfig，运行时由 DataStore 读取（首次启动引导输入），BuildConfig 只留 debug 默认值；② `allowBackup=false` 或配置 dataExtractionRules 排除数据库；③ 补设置页（BYOK 输入 + 模型/BaseUrl 配置），这也是方案"记忆数据库导入导出一等公民"（方案 2.2 节）的前置 UI 容器。
- **优先级**：高（隐私红线）。

## 4.G 【缺失】MemoryExtractor 无节流，每条消息一次 LLM 调用
- **现状**：`MemoryExtractor.kt:30`（≥8 字符即触发）+ `ChatViewModel.kt:267`（每轮消息后调用），无冷却窗口、无批量合并；且 `parseAndStore` 只做批内去重（`distinctBy`），与库内既有记忆无查重 → 条目只增不减，等 M2.3 梦系统才治理。
- **建议**：加"距上次抽取 >3 分钟或积攒 ≥3 轮"的节流门，抽取时附带最近 N 条未抽取消息的批量上下文，抽取成功后记录 watermark。
- **优先级**：中。

## 4.H 【不完整】M2.1 缺截帧组件实现规格
- **现状**：方案 4.1 给了 ExecutionTreeExtractor/TextInputExecutor/ServiceHolder 的完整代码，唯独 HybridGroundingEngine 的 VLM 兜底所需的 `FrameCaptureResult` 无实现路径。minSdk 26 < `AccessibilityService.takeScreenshot`（API 30+），需要 MediaProjection 兜底方案。
- **建议**：M2.1 明确双通道截帧：API 30+ 走 `takeScreenshot`，低版本走 MediaProjection（需用户授权，首次申请时机放进设置页引导）。否则 VLM 兜底在部分真机上直接不可用，验收标准"坐标误差 ≤1px"无从谈起。

## 4.I 【不完整】悬浮窗服务的进程优先级未定义，任务代行有中断风险
- **现状**：`CompanionOverlayService` manifest 声明 `foregroundServiceType="specialUse"`（`AndroidManifest.xml:78`）但**从不调用 startForeground**，实际由 `KeepAliveService.kt:82` 以 `startService` 拉起的后台服务运行；START_STICKY 复活后优先级更低。
- **影响**：方案 4.5 要把"任务执行态 UI + 中止按钮"挂在这个服务上，执行中被系统杀掉 = 代行任务静默中断，且自愈无门。
- **建议**：任务执行期间将 CompanionOverlayService 提升为前台（带轻量通知），执行完降级；或在 HelixGuiCoordinator 内独立持有一个前台服务承载执行态。
- **优先级**：高（属于 M2.2 的隐藏前置条件，方案未列）。

## 4.J 【缺失】测试体系偏科 + 稳定性监控完全空白
- **现状**：249 个单测全部为 JVM 单测（Robolectric），无 androidTest（instrumented）目录与用例，无 benchmark；全工程无崩溃捕获、无日志落盘，`println` 散落（`XiaoxiLlmClient.kt:158`、`PerceptionPipeline.kt:176`）。方案 7.2 的"真机复杂场景用例库"没有自动化载体，验收靠手点。
- **建议**：① M2.2 起为 HelixGuiCoordinator 补 androidTest 骨架（模拟器即可跑）；② 落地本地崩溃捕获（Thread.setDefaultUncaughtExceptionHandler → Room/文件环形落盘 + 下次启动可导出），尊重单用户隐私定位不上报云端；③ 用 Log 替换 println。
- **优先级**：崩溃捕获=高；androidTest=中。

## 4.K 【低优先级补充】感知层小项
- 重复脱敏：`XiaoxiAccessibilityService.kt:210` 已 sanitize，`PerceptionPipeline.kt:132` 再 sanitize 一次（无害，纯浪费，可留一处）。
- `UsageStatsTracker.kt:125` 2s 轮询 `queryEvents`，亮屏常开；可考虑拉长至 3-5s 或对 `ScreenState.ON`（未解锁）也跳过。
- `gradle.properties` 建议补 `org.gradle.configuration-cache=true`（AGP 8.7 + Kotlin 2.0 已支持）。
