## 三、严重问题（5 项）

### 严重#1：MIGRATION_1_2 不完整 → v1 老用户升级必崩（数据安全，最高优先级）

- **位置**：`XiaoxiDatabase.kt:58-85`（迁移体）、`UnspokenThoughtEntity.kt:23-53`（当前实体）、`RoomMigrationTest.kt:72-83`（测试基线）
- **问题描述**：当前 `UnspokenThoughtEntity` 含 `trigger_context` / `decay_score` / `target_scenario` 三列且**不含** `curiosity` / `warmth`；而 `RoomMigrationTest` 手写的 v1 基线恰好相反（有 curiosity/warmth，无前三者）。`MIGRATION_1_2` 只创建了 `worldview_entities`、`scheduled_alarms` 两张新表并为 `self_experiences` 加列，**对 `unspoken_thoughts` 没有任何 ALTER/DROP**。
- **影响**：任何装有 v1 schema 的设备（包括已安装旧版的真机）升级到 v2 后，Room 打开数据库时 schema 精确校验失败 → `IllegalStateException: Migration didn't properly handle unspoken_thoughts` → **App 启动即崩溃，且每次启动复现**。双轨记忆库对用户不可达。
- **测试为何没拦住**：`RoomMigrationTest` 用手写 `SupportSQLiteOpenHelper.Callback(2)` 执行迁移后只做了 `self_experiences` 数据断言与新表写入验证，**从未用 Room 实例打开迁移后的库**（Room 的迁移校验根本没发生）；且手写 v1 基线本身就与真实 v1 实体存在出入，基线失真。
- **建议处理**：① 补齐迁移：`ALTER TABLE unspoken_thoughts ADD COLUMN trigger_context TEXT` / `decay_score REAL NOT NULL DEFAULT 1.0` / `target_scenario TEXT`，并按需处理 curiosity/warmth 列（与真实 v1 git 历史核对后决定 DROP 或保留）；② 测试改用 `MigrationTestHelper` + `app/schemas/` 下的 v1 JSON（构建配置 `build.gradle.kts:129-133` 已导出 schema，具备条件）打开验证，杜绝手写基线漂移；③ 在升级前先确认目标真机当前安装版本，若已是 v1 必须先修再发。

### 严重#2：备份排除规则数据库名失配 → 亲密记忆随云备份外流（隐私，P5 核心目标失效）

- **位置**：`data_extraction_rules.xml:5-7`、`backup_rules.xml:4-6` vs `XiaoxiDatabase.kt:55`
- **问题描述**：两份备份规则排除的库名均为 `xiaoxi_database`(-shm/-wal)，而实际 `DATABASE_NAME = "xiaoxi_aether.db"`。排除路径全部失配。
- **影响**：`user_memories` / `self_experiences` / `unspoken_thoughts` / `chat_dialogues` / `worldview_entities` / `scheduled_alarms` 六张表及 WAL/SHM **完全未被排除出 Android 云备份与 D2D 迁移**——这正是 P5 要防的"亲密双轨记忆外流"，目前形同虚设。`files/crashes` 与 `xiaoxi_byok_prefs.xml` 两项排除路径是匹配的（但后者对应的 BYOK 仓库本身是死代码，见严重#3）。
- **建议处理**：两份规则的库名改为 `xiaoxi_aether.db` / `xiaoxi_aether.db-shm` / `xiaoxi_aether.db-wal`；补一条单测对 `DATABASE_NAME` 常量与 XML 内容做一致性断言（`BackupAndByokTest` 现有框架即可扩展），防止未来改名再度失配。

### 严重#3：BYOK 完全未接线（零消费死代码）+ API Key 仍明文打包（P5/P3 双缺口）

- **位置**：`ByokSettingsRepository.kt`（全文）；`ChatViewModel.kt:42`、`XiaoxiApplication.kt:104-106`、`OverlayExpandViewModel.kt:41-45`；`app/build.gradle.kts:35/:40`
- **问题描述**：
  1. Grep 全主源码，`ByokSettingsRepository` / `getEffectiveLlmConfig` **仅命中定义文件自身**——`XiaoxiApplication` 没有装配它，三个 LlmConfig 默认值处全部直取 `BuildConfig.DEEPSEEK_API_KEY`，没有任何 UI 入口调用 `saveCustomApiKey` 系列。整个 BYOK 抽象是"写了但从未通电"。
  2. `build.gradle.kts:35` API Key 仍为编译期常量打进 APK；`:40` `isMinifyEnabled = false`，release 未混淆未收缩——与 PROGRESS_TRACKER.md:20 将 "R8" 写入 M2.1 "已全绿验收" 直接矛盾。`proguard-rules.pro` 规则文件已备好却未启用。
- **影响**：反编译 APK 一键提取 Key；用户自定义 Key 的产品能力为零；提交记录与验收文档的可信度受损。
- **建议处理**：① `XiaoxiApplication` 装配 `ByokSettingsRepositoryImpl`，`ChatViewModel` / `OverlayExpandViewModel` / `backgroundLlmConfig` 统一改为消费 `getEffectiveLlmConfig()`（或 collect settings 流动态更新）；② 补 BYOK 设置 UI 入口；③ release 启用 `isMinifyEnabled = true` + `isShrinkResources = true`，在真机回归后（proguard 规则已备好）再发版；④ 若 Key 必须内置，考虑 `local.properties` 之外再加 NDK 存放或运行时拉取等加固（混淆后仍非绝对安全，需知情取舍）。

### 严重#4：CoordinatorAction.Type 输入链路断裂 → 文本代行 100% 失败（M2.1/M2.2 核心功能）

- **位置**：`HelixGuiCoordinatorImpl.kt:336-343`（恒传 `node = null`）、`TextInputExecutor.kt:30-37`（优先路径要求 node != null）、`TextInputExecutor.kt:46`（`node?.performAction(ACTION_PASTE) ?: false`）
- **问题描述**：Coordinator 执行 Type 动作时调用 `textInputExecutor.injectText(node = null, targetBounds = bounds, text = ...)`。`node = null` 导致：① ACTION_SET_TEXT 优先路径被整体跳过；② 降级路径虽然完成了备份剪贴板 → 写入 → 拟人点击 → delay(100)，但最后一步 PASTE 作用在 null node 上**恒返回 false**，finally 恢复剪贴板。整个过程用户只会看到小汐点了一下输入框，**文本从未被输入**。
- **影响**：`input_text` 工具、悬浮窗草稿代发、E2E 场景 1（微信草稿）在真机上全部失效。单测未暴露是因为 `TextInputExecutorTest` 只覆盖了 node 非 null 的路径，`EndToEndMilestone24VerificationTest` 用的是 mock 协调器。
- **建议处理**：`executeUiElementAction` 中 `GroundingResult.Found` 已持有 `refNode`（`HelixGuiCoordinatorImpl.kt:251-253`），把它一并传入 `injectText(node = refNode, ...)` 即可打通优先路径；降级路径的 PASTE 也应基于 refNode 执行。补一条 node=null 场景的失败语义测试，并在修复后于真机跑一次微信草稿场景。

### 严重#5：精确闹钟无权限声明且无降级 → Android 14+ 上 schedule_wake 必抛 SecurityException

- **位置**：`ScheduleWakeManager.kt:40-44`（`setExactAndAllowWhileIdle`）、`AndroidManifest.xml`（无 `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM` 声明）、`NativeToolAgent.kt:347-364`（schedule_wake 分支无 try-catch）
- **问题描述**：targetSdk=35 且未声明精确闹钟权限时，Android 14+ 对新装应用默认**拒绝** `SCHEDULE_EXACT_ALARM`，直接调用 `setExactAndAllowWhileIdle` 抛 `SecurityException`。代码既没有 `canScheduleExactAlarms()` 预检，也没有降级到 `setWindow` 的路径；异常从 `alarmScheduler.scheduleAlarm` 一路穿透（`NativeToolAgent.executeToolCall` 无兜底），直到 `ChatViewModel` 的最外层 catch 才被接住。
- **影响**：主方案 M2.4 的"自定闹钟活水"特性在 Android 14+ 真机上**首次调用即失败**，且错误文案是"通信异常"级别的笼统报错，用户不可理解。
- **建议处理**：① manifest 声明 `SCHEDULE_EXACT_ALARM`（或直接用 `USE_EXACT_ALARM`，闹钟类应用专属权限，免引导）；② `scheduleAlarm` 内做 `canScheduleExactAlarms()` 预检，false 时降级 `setWindow` 并在返回的实体/日志中标注"非精确"；③ `NativeToolAgent.executeToolCall` 整体包 runCatching，把工具执行异常转成 `isSuccess=false` 的 tool 结果回传给 LLM，保持闭环自愈能力。

## 四、中等问题（7 项）

### 中等#1：主界面 Function Calling 闭环未接线（toolAgent 未传入 ChatViewModel）

- **位置**：`MainActivity.kt:24-36`
- **问题**：工厂创建 ChatViewModel 时未传 `toolAgent = app.nativeToolAgent`（该实例在 `XiaoxiApplication.kt:157-161` 已装配但闲置），也未传 `handoffManager`。`ChatViewModel.kt:247` `tools = toolAgent?.declaredTools` 将传 null → 主界面对话**永远不会下发工具定义**，M2.4 "打通聊天链路 Tool 多轮闭环"在主入口实际不成立（悬浮面板 `sendQuickMessage` 同样不带工具）。
- **影响**：声明式验收（"打通 Function Calling 闭环"）与真实用户路径不符； HelixGuiCoordinator / NativeToolAgent / 六个工具声明目前只被测试触达。
- **建议**：MainActivity 工厂补传 `toolAgent` 与 `handoffManager`；补一条"工厂装配完整性"测试（反射断言关键依赖非空），防回归。

### 中等#2：Watchdog 自愈退避机制断裂 + 跨任务状态污染

- **位置**：`HelixGuiCoordinatorImpl.kt:191/:216`（fingerprint 恒传 `0L`）、全文未调用 `watchdog.recordRecoveryAttempt(...)`、`executeTask` 未调用 `watchdog.reset()`；`SelfHealingWatchdog.kt:124-126`
- **问题**：① `recoveryAttempts` 只在 `recordRecoveryAttempt` 中递增，而 coordinator 从不调用 → `maxRecoveryAttempts=3` 的 Unrecoverable 上限**永不触发**，自愈可无限重试；② watchdog 是 Application 级单例，任务间不 reset → 上一个任务的 stepHistory / lastFingerprint 污染下一个任务；③ fingerprint 恒 0 使"连续同指纹卡死"检测语义失真——任何连续 3 次 inspectStep 调用都会被判为 STUCK_LOOP（碰巧为失败兜底，但把"三次不同原因的失败"误判成"卡死"）。
- **建议**：失败路径上用真实页面指纹（可对 `dump.nodes` 的 text/bounds 做哈希）替代 0L；applyRecoveryAction 成功后调 `recordRecoveryAttempt(verdict.anomaly)`；`executeTask` 入口调用 `watchdog.reset()`。

### 中等#3：ScheduleWakeReceiver 协程异常无兜底 → 可崩进程

- **位置**：`ScheduleWakeManager.kt:74-86`
- **问题**：`goAsync()` + 裸 `CoroutineScope(Dispatchers.IO)` 无 `CoroutineExceptionHandler`。若 `onWakeTriggered` 内 DB 操作抛异常，未捕获异常沿协程交给线程默认 handler → 触发 `XiaoxiCrashHandler` → **进程终止**。M2.5 声称的"goAsync 修复"只解决了 finish() 时序，未兜异常。
- **建议**：`CoroutineScope(SupervisorJob() + Dispatchers.IO + CoroutineExceptionHandler { _, e -> XiaoxiLog.e(...) })`；异常时仍保证 `pendingResult.finish()`（现有 finally 已覆盖，但需确保异常不再外泄）。

### 中等#4：refreshIcebreaker 旁路绕过主动总线配额

- **位置**：`CompanionOverlayService.kt:84`（onStartCommand 无快照分支）、`:350`（挂载成功后）→ `OverlayExpandViewModel.kt:94-100`
- **问题**：`refreshIcebreaker()` 直接从 DAO 取最高紧急念头展示，**不经过 ProactiveBubbleCoordinator 的每日配额 / 退避惩罚 / 沉默裁决**。主方案断层三（"主动性总线被悬浮窗绕过"）在此残留一半：感知驱动路径已被接管，但这条"首帧兜底"旁路仍可无配额弹气泡。
- **建议**：旁路改为调用 `coordinator.coordinate(...)`（或为协调器增加"首帧强制裁决"入口）；至少在 refreshIcebreaker 展示后手动计入配额。

### 中等#5：确认等待忙轮询 + 协程取消时状态不归位

- **位置**：`HelixGuiCoordinatorImpl.kt:307-316`
- **问题**：`while (!confirmed && !cancelled && !isCancelled) { ... delay(50) }` 最长 5 分钟 6000 次轮询，应改 `CompletableDeferred` / `suspendCancellableCoroutine`；且外层协程被取消时 `delay` 抛 CancellationException 直接上抛，`_state` 停留在 `AwaitingUserConfirmation` 不会归位 Idle，下次任务前状态残留。
- **建议**：Deferred 化等待；`try/finally` 中保证取消路径把状态置回 Idle。

### 中等#6：屏幕尺寸硬编码 1080×2400，装配侧未覆盖

- **位置**：`HelixGuiCoordinatorImpl.kt:60-61`（默认值）、`XiaoxiApplication.kt:147-155`（装配时未传）
- **问题**：`screenWidthProvider/screenHeightProvider` 用默认硬编码，Swipe 方向坐标换算与接地比例计算在非 1080×2400 设备上全部错位；单用户项目若冷冷设备恰好是其他分辨率，滑动代行将系统性点偏。
- **建议**：装配处用 `Resources.getSystem().displayMetrics` 或 `WindowManager.currentWindowMetrics`（API 30+）注入真实尺寸。

### 中等#7：MemoryExtractor 触发后失败丢批

- **位置**：`MemoryExtractor.kt:105-113`（锁内先 clear + 清 watermark）与 `:119-126`（LLM 失败 catch 返回 0）
- **问题**：`pendingTurns` 在发起 LLM 请求**之前**被清空；请求失败（网络/超时/解析）时本批已积攒的对话上下文**永久丢失**，watermark 也已被推进。注释声称"失败静默不影响对话"成立，但代价是静默丢数据。
- **建议**：失败时把 batchContext 回填 pendingTurns（或仅推进 watermark 不清队列，成功后再清）。
