## 二、问题清单（问题位置—原因—修复建议）

### 问题 1（P1）性能断言测试偶发失败，commit message「全绿」表述失实

- **问题位置**：`app/src/test/kotlin/com/lirica/android/database/memory/MemoryVectorStoreTest.kt:109`
  `testScaleAndPerformanceWith5000Vectors` 抛出 `AssertionError: 检索耗时应低于 10ms`。全量日志证据：`881 tests completed, 1 failed`。
- **原因**：该测试对 5000×512 维向量做 20 次检索，用 `System.currentTimeMillis()` 自计时并断言平均 <10ms，**只预热 1 次**。全量跑测时它与 880 个测试同 JVM 执行，GC 停顿 / JIT 未充分预热 / CPU 负载抖动导致均值越线。三个佐证：
  1. **隔离重跑 4/4 全部通过**（11s，含该用例）；
  2. `MemoryVectorStore` **不在 8dc910f 改动清单内**（`git show 8dc910f --stat` 无命中），非本次回归；
  3. 失败信息是 AssertionError 而非任何功能断言失败。
- **修复建议**：
  1. 把这类墙上时钟性能断言改为**软断言**：超阈值只 `println` 警告不 `fail`（性能护栏的意义是暴露趋势，不是卡构建）；或改用 `org.junit.rules.Timeout` 表达硬上限；
  2. 若保留硬断言：预热 3~5 次再计时，并放宽到 P95 口径（记录 20 次耗时取分位数）；
  3. PROGRESS_TRACKER / commit message 中「881项单测全绿」应修正为「881项单测，1项性能断言环境敏感（隔离重跑通过）」，避免下次复审再对不上。

### 问题 2（P2）LAUNCH_APP 注释承诺的「金融包名二次拦截」在 Intent 通道未兑现

- **问题位置**：
  - `app/src/main/kotlin/com/lirica/android/automation/policy/SystemActionCatalog.kt:181`
    `note = "前台应用拉起；若目标为金融/支付包名，仍由包名闸门二次拦截"`
  - `app/src/main/kotlin/com/lirica/android/automation/policy/SafetyPolicyEngine.kt:209-260`
    `evaluateIntent()` 全程**没有调用 `gatekeeper.evaluate()`**，也没有任何包名检查（对比 UI 通道 `evaluateUi()` 在 :163-179 明确走了第一层金融零容忍闸门）。
  - `app/src/main/kotlin/com/lirica/android/automation/intent/IntentActionDispatcher.kt:103-110`
    `LaunchApp` 直接 `getLaunchIntentForPackage(action.packageName)` 执行，执行点同样无兜底。
- **原因**：金融闸门只接入了 UI 通道；Intent 通道从 catalog（LAUNCH_APP = LOW + autoPass）→ 引擎（evaluateIntent）→ 派发器全链无包名校验。**金融/支付 App 可被无感拉起**，与 :181 注释承诺不符。
- **风险边界（为什么只是 P2 不是 P1）**：拉起后任何 UI 操作都会经 `evaluateUi()` 携带 `currentPackage` 撞上闸门（SafetyPolicyEngine.kt:164-179），且 `ExecutionTreeExtractor` 的 PRIVACY_BLACKOUT 会切断金融 App 内的节点采集。残余风险限于「拉起动作本身」。
- **修复建议**（二选一，推荐前者）：
  1. `evaluateIntent()` 对携带 `packageName` 的动作（`LaunchApp`、`OpenSettings`）补一层：`gatekeeper.evaluate(ProposedAction(actionType = "LAUNCH_APP", currentPackage = action.packageName))`，命中 PhysicalBlocked 直接返回 `SafetyDecision.Blocked`——兑现注释承诺；
  2. 或把 :181 注释改为实情：「金融包名不拦截；进入应用后的 UI 操作由 UI 通道闸门与采集中断兜底」。

### 问题 3（P2）具身反馈双通道未打通，闭环事件在运行时全部落入 NoOp

- **问题位置**：
  - `app/src/main/kotlin/com/lirica/android/automation/coordinator/AutonomousActionLoop.kt:74`
    `feedback: ActionVisualFeedbackListener = NoOpActionVisualFeedbackListener`——闭环内部大量 `emit`（REPLAYING :163/:238、USER_INTERRUPTED :316、StepProgress :396、FAILED :793 等）都走这个参数。
  - `app/src/main/kotlin/com/lirica/android/automation/coordinator/HelixGuiCoordinator.kt:122,145,577`
    协调器自己持有独立的 `feedbackHub` 并对外提供 `registerFeedbackListener()`。
  - `app/src/main/kotlin/com/lirica/android/LiricaApplication.kt:531-571`
    构造两者时**均未传 feedback**。
- **原因**：M5.1 范围定为「接口先行，悬浮窗后续接入」，NoOp 默认本身符合当期范围；但两个组件各持**互不相通的独立通道**。后续接入悬浮窗时若只调 `helixCoordinator.registerFeedbackListener()`，将只能收到协调器侧的 TouchTrace/BubbleState，**闭环侧的全部具身事件（用户抢占、宏回放进度、步骤进度）永远收不到**——这是给 M5.4/悬浮窗接入埋的接线陷阱，且现在看不出任何异常（事件被静默丢弃）。
- **修复建议**：在 `LiricaApplication` 先建共享中枢再注入两端：
  ```kotlin
  val feedbackHub = com.lirica.android.automation.feedback.ActionFeedbackHub()
  // AutonomousActionLoop(..., feedback = feedbackHub)
  // HelixGuiCoordinatorImpl(..., feedbackListener = feedbackHub)
  ```
  协调器内部会把传入 listener 包进自己的 hub（HelixGuiCoordinator.kt:145），嵌套多播仍满足「UI 异常不击穿执行链路」约束（双重 runCatching 隔离）。改完后建议补一条契约测试：向共享 hub 注册的监听器能同时收到协调器与闭环两侧事件。
