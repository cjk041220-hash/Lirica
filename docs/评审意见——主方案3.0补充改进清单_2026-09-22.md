## 二、七项"会让里程碑验收不通过"的硬前置（P0 级，方案全未列）

### #1 `accessibility_service_config.xml` 缺 `canTakeScreenshot` —— M3.2 第一行代码就会抛异常

- **位置**：`app/src/main/res/xml/accessibility_service_config.xml:2-10`
- **现状**：只声明了 `canRetrieveWindowContent="true"` 与 `canPerformGestures="true"`，**没有 `android:canTakeScreenshot`**
- **后果**：Android 11+ 上 `AccessibilityService.takeScreenshot()` 必返回 `ERROR_TAKE_SCREENSHOT_NO_ACCESSIBILITY_ACCESS`。方案 3.3.1 的代码原样落地 → 每次 `captureScreenJpeg()` 都走 `onFailure` → 恒 `null` → M3.2 的三条验收指标全部不成立
- **建议**：加 `android:canTakeScreenshot="true"`；若要走 M3.3 的"物理按键"另一路，同时评估 `android:accessibilityFlags` 补 `flagRequestFilterKeyEvents`（收按键需 `flagRequestFilterKeyEvents` + `onKeyEvent` 覆写）。这两条属 M3.2/M3.3 的**隐式第一任务**

### #2 无障碍服务的架构契约与 M3.1/M3.3 直接冲突

- **位置**：`XiaoxiAccessibilityService.kt:34` 类头注释「**5. 严格只读隔离：绝不调用任何 performAction()**」
- **冲突**：方案 3.1.1 的 `AccessibilityExecutionBackend` 要调 `performAction` / `dispatchGesture`；3.2's 截屏也要在这个服务内
- **后果**：这不是语法问题，是**架构契约被悄悄推翻**。现有代码里 `onAccessibilityEvent` 只入队、后台协程只读树（`:127-226`），整条设计都在"绝不写"这个假设上。加写入通道后，Binder 线程约束、脱敏时序、隐私熔断的成立条件都要重审
- **建议**：方案补一节「感知-执行双模契约」，明确：① 是否拆成两个 `AccessibilityService`（读一个/写一个，可分别让用户授权）；② 若不拆，`performAction` 必须走独立 IO 调度器并对 `isPrivacyFusing` 再校验一次

### #3 模型看不到屏幕—— **本方案最大的洞**

- **现状证据**：
  - `MapBasedPromptAssembler.kt:115-144`（Level 4「即时情境感知」）注入给模型的只有三样：**前台应用名 + 停留分钟 + 屏幕开合状态 + 最新一条通知**
  - 无障碍节点树（`PageContentSnapshot.nodes`，含文本与 bounds）**从未进入任何 prompt**——全仓无消费方
  - `NativeToolAgent.kt:49-199` 共 6 个工具（`open_app` / `click_element` / `input_text` / `swipe` / `task_finish` / `schedule_wake`），**没有任何"读屏"工具**
  - 工具返回体只有自然语言（如 `:254-257`「点击操作完成: …」），**不含动作后的界面观测**
- **后果（三条，逐条致命）**：
  1. 接地失败或多候选时，模型**无从选择**——`HybridGroundingEngineImpl` 能返回 `Ambiguous(candidates)`（`:64-70`、`:129-135`），但这份候选列表根本没送到模型面前
  2. 动作结果**无法校验**——`task_finish` 的 `summary`（`:341-346`）只能靠模型编，这正是"代行幻觉"的结构性来源
  3. M3.3 的动作分块 = **让盲人一次走三步**。分块把 RTT 省下来了，但每一步的接地仍是纯本地猜测
- **建议（新增 M3.0，排在 M3.3 之前）**：
  - 新增 `read_screen` 工具：返回**净化后**的节点摘要（文本 + 归一化 rect + resourceId，按 token 预算截断到 N 条/总长上限）
  - 每次动作完成后，由 `NativeToolAgent` 自动把"动作后界面摘要"拼进 `tool` 消息正文 → 形成 `observe → act → observe` 闭环
  - 该通道必须过 `PrivacyBreaker.sanitizePageSnapshot()`，且受 `isPrivacyFusing` 硬熔断
  - 参考 `Mobile-Agent v2` 的"进度里程碑"思路（方案 1.1 已引用），但**它压缩的是执行历史，不是观测通道**——方案把两者混为一谈了，观测通道是缺的

### #4 隐私：M3.2 的全屏截帧**绕过**了 `PrivacyBreaker`

- **位置**：`PrivacyBreaker.kt:87-121`（只处理 `PageContentSnapshot` 的**文本节点**）；`PerceptionPipeline.kt:70/134`（`isPrivacyFusing` 已算出）；`ScreenCaptureManager.kt`（无门控）
- **问题**：截帧产物是 `ByteArray` 原始像素，`PrivacyBreaker` 对像素无能为力。方案 3.3.3 的 L2 要把**整屏 JPEG 上传云端 VLM**
- **后果**：在银行 App、聊天界面、验证码短信弹出的瞬间触达 L2 → **整屏内容（含账户余额、聊天记录、验证码）原样上传到第三方模型 API**。这直接击穿项目自我定位的"PII 泄露率 0.000%"红线（`PrivacyBreaker.kt:8`）
- **建议（三闸门，缺一不可）**：
  1. 截屏前硬门控：`if (snapshot.isPrivacyFusing) return null`（复用已有的 `PrivacyBreaker.SENSITIVE_PACKAGES` 黑名单 `:23-55`）
  2. 上传前本地像素级遮罩：对密码框/金融区域的 bounds 打马赛克（节点树里 `isPassword` 与敏感包名都是现成信号）
  3. L2 上传需**用户显式开关 + 每次可见提示**（默认关闭）。方案 2.1 架构图里写了"隐私熔断与安全脱敏护栏"，但第三章**通篇没有落到实现**——这句话目前是空头承诺

### #5 `open_app` 只有 17 条硬编码映射，且 Manifest 缺 `<queries>`

- **位置**：`NativeToolAgent.kt:394-415`（`KNOWN_APP_PACKAGES` 17 条）、`:417-423`（`resolvePackageName` 兜底把**中文名当包名返回**）；`AndroidManifest.xml`（无 `<queries>` 元素）
- **后果**：`.resolvePackageName("饿了么")` → 返回 `"饿了么"` → `IntentAction.LaunchApp(packageName="饿了么")` 必失败。而 targetSdk 35 下，即使改用 `PackageManager.queryIntentActivities` 做标签检索，**不声明 `<queries>` 也会返回空列表**（Android 11+ 包可见性）
- **为什么现在才炸**：M3.2/M3.3 把"操控"推到台前，`open_app` 是用户看到的第一个动作。这是评测第一印象的瓶颈
- **建议**：① Manifest 加 `<queries>`（launcher intent + 常用包名白名单）；② 用 `queryIntentActivities` + `getApplicationLabel` 做真实标签索引，缓存到 Room；③ 保留硬编码映射作为"冷启动秒开"的加速表；④ 拼音/别名索引（"E了么"/"ele"）

### #6 删掉 UsageStats 轮询后，"未开无障碍"设备将彻底失去前台感知

- **位置**：`UsageStatsTracker.kt:122-156`（唯一轮询源）；`XiaoxiAccessibilityService.kt:127-143`（事件源，**当前并不产出 `ForegroundAppInfo`**）
- **问题**：方案 3.2.1 只说"彻底消除轮询"，未定义降级。而 `PACKAGE_USAGE_STATS` 与无障碍是**两个独立授权**——只开了前者、没开后者是完全可能的用户状态
- **另外两个未考虑的边界**：
  - `TYPE_WINDOW_STATE_CHANGED` 的 `packageName` 在系统弹窗/通知栏下拉时会是 `android` / `com.android.systemui`，会**污染**前台判定（现有轮询查 `ACTIVITY_RESUMED` 反而更准）
  - `dwellDurationMs`（`:148`）的累计逻辑依赖固定轮询间隔，改事件驱动后必须重算
- **建议**：事件驱动为主 + 轮询降级为辅（无障碍未开时自动落到 3~5s 轮询）；事件侧过滤 systemui / 权限对话框包名；`dwellDurationMs` 改为按事件时间戳差值累计

### #7 M3.1 要动 `ChatViewModel`，但方案交付清单里没有

- **现状**：`ByokSettingsRepository.kt:22-25` 自标 `[EXPERIMENTAL / 未接线]`；主链路仍直取 `BuildConfig.DEEPSEEK_API_KEY`（上一轮复检轻微#4 已指出）
- **连锁反应**：M3.1 要移除 `build.gradle.kts:17-24` 的 `error()` 硬阻断 → 未配置 Key 时 `BuildConfig.DEEPSEEK_API_KEY` 变成**空字符串** → 主对话链路拿到空 Key 直接 401
- **建议**：M3.1 交付清单显式补两条：① `ChatViewModel` / `MapBasedPromptAssembler` 全部改走 `ByokSettingsRepository.getEffectiveLlmConfig()`；② 首次启动无 Key 时的**引导 UI + 不可用态降级**（不能白屏、不能 401 报错裸奔）

## 四、里程碑排序建议

方案的顺序（BYOK → 视觉 → 操控 → 人格）在**技术上**是合理的（M3.1 的网关是 M3.2 云端 VLM 与 M3.4 入梦的共同前置）。但从**产品收益**看有两处该动：

```
建议顺序：
  M3.1  外部 API 解放（保留第一）           ← 它是后续三项的前置，且能立刻解决"用户只能吃我的 Key"
  M3.4a 动作伴随语（从 M3.4 拆出，提到第 2 位） ← 1 天工作量、零技术风险，直接兑现产品的核心价值
  M3.0  观测闭环（新增：read_screen + 动作后观测注入） ← 不做这个，M3.3 的宏动作就是把盲人推得更快
  M3.2  视觉感知（补 #1 canTakeScreenshot、#4 隐私闸门）
  M3.3  操控升维（Shizuku + execute_macro，补 #2 契约、#5 包解析）
  M3.4b 人格维持与全域监视（入梦 LLM 化 + 硬件总线 + 零轮询）
  M3.5  端侧向量检索（从 M3.4 拆出，见下）
```

**为什么"动作伴随语"该排第 2**：它是全案唯一直接服务于产品定位（"活人感"）的改动，成本 1 天、风险为零，且不依赖任何新依赖。把它压在 M3.4（要等三个里程碑的基础设施）是纯粹的收益延迟。

**为什么"端侧向量检索"该拆成独立里程碑**：
- 它同时引入 **Room schema 迁移（v2→v3）+ 384 维新字段**、**ONNX Runtime Mobile 原生库**、**一个 Kotlin 侧的 BERT/WordPiece tokenizer**（全仓目前没有任何 tokenizer，这是最容易被低估的工作量）、**R8 keep 规则**（JNI 反射）
- 它解决的痛点（"纯文字模糊匹配对近义词无效"）目前**没有被量化**：`MemoryScorer` 已有 6 维打分，话题匹配用字符 2-gram（`:48-55`）
- 建议设**先证伪门槛**：拿 50 条标注样本测现有 bigram 的召回率；若达标则不做，若明显不足再上向量——避免为了一个未验证的痛点投入最重的一块工程量

## 五、项目还需要什么（方案完全未覆盖的 8 项）

### 1. 首次启动的权限引导向导 + 权限体检面板（最影响"能不能用起来"）
需要用户在**至少 6 个分散的系统页面**手工开启：无障碍服务、通知使用权、悬浮窗、使用情况访问、电池优化白名单、（M3.3 后）+ Shizuku 激活。
现有零件三块——`XiaoxiAccessibilityService.createSettingsIntent()`（`:75-79`）、`UsageStatsTracker.createPermissionSettingsIntent()`（`:63-67`）、`BatteryOptimizationHelper`——**但没有组装**。`MainActivity.kt` 目前只有 `ChatScreen` 一个界面，无导航外壳、无设置页。
建议：一个 Compose 向导（逐项状态检测 + 一键跳转 + 回来自动刷新），以及一个"体检面板"常驻入口。

### 2. 成本与用量闸门
BYOK 多档模型（方案 3.5.3 的四档）× 动作分块（连续多轮 tool 调用）× 夜间入梦批处理 × （未来的）向量检索 = 调用量成倍放大。
方案只在 3.5.3 写了"兼顾最强心智表现与极致使用成本"，**没有任何预算护栏**。
建议：本地计量页（按 tier 统计 token 与估算费用）+ 单日预算上限 + 超限自动降级到 cheapest tier。没有这个，用户把 Claude Sonnet 配成 chat tier 会直接烧钱。

### 3. 并发治理
M3.1 之后将同时存在三条独立 LLM 链路：chat tier（用户交互）、agent tier（代行）、dream tier（夜间 Worker）。加上 WorkManager 的补跑语义（任务失败会重试），**同一批记忆可能被两个 dream cycle 同时处理**。
建议：单飞锁（`SubconsciousDreamWorker` 已在，但需显式互斥）+ 全局并发闸门（避免夜间批量把配额打满）。

### 4. 数据主权：导出与一键清空
记忆、日记、世界观、经历库是本产品最核心的资产沉淀，但**没有任何导出/导入/清空入口**。2.0 方案里提过"记忆数据库导入导出一等公民"，3.0 掉了。
建议：JSON（结构化，可再导入）+ Markdown（人可读，可交付）双格式导出；一键清空需二次确认。

### 5. 版本与构建治理（上一轮 P9 未做）

## 七、我的两项建议

### A. 端侧向量检索（3.4.3）：**建议不在 3.0 立项，改为设触发器**

**不建议现在做的四条理由**：

1. **工程风险与收益不成比例**：它同时引入 ① Room schema 迁移（v2→v3 + 384 维新字段）② ONNX Runtime Mobile 原生库 ③ **一个 Kotlin 侧的 BERT/WordPiece tokenizer**（全仓目前零 tokenizer，工作量最容易低估）④ R8 keep 规则（JNI 反射，而 R8 已启用）。这是全案最高风险项。
2. **与"活人感优先"无关**：检索质量影响的是"她记不记得住"，而当前影响"她记不记得住"的主要矛盾**不是相似度，是记忆条目质量**——`BeliefRevisionEngine` 的硬编码消歧（`BeliefRevisionEngine.kt:20-29` 只认咖啡/吃辣/搬家/单身四组）会让错误事实长期驻留。先把消歧 LLM 化，收益远大于换检索算法。
3. **分发成本落在你身上**：给朋友装，包体从 2.14MB 跳到 20MB 级（+ML Kit 8~12MB、+ONNX 5~10MB），ABI split / 兼容问题都要你来处理。
4. **痛点未量化**：`MemoryScorer` 已有 6 维打分，话题匹配用字符 2-gram（`MemoryScorer.kt:48-55`）。在 200 条量级的记忆库上，2-gram 对中文近义词并非完全无效（"喝咖啡"vs"咖啡"、"加班"vs"工作到很晚"都能命中子串）。

**替代方案与触发器**（如果将来真要做，按这个门槛）：

- 先做 **M3.4 的入梦 LLM 化**（消歧 + 提炼），它同时改善记忆质量与召回可读性
- 建一个 **30 条标注样本集**（query → 期望命中的记忆），测现有链路 top-3 命中率
- **命中率 < 80% 才立项 M3.5**；≥ 80% 就把这块工作量投到别处

### B. `backend/` 定位：**建议"冻结 + 能力清点"，而不是简单标注"参考源"**

**先纠正一个事实**：方案基线写"**全仓** 100% Native Kotlin"——**不成立**。仓库根下是 `app/`（Kotlin，唯一 Gradle 模块）+ `backend/`（Python FastAPI，136 个文件）。这句应改为"**Android 侧** 100% Native Kotlin"。

**但更重要的发现**：我清点后发现，`backend/` 远比"参考源"这三个字所暗示的更有分量——**它是一个功能更完整的 1.0 产品，Android 侧在原生重构中丢掉了整整一层能力**：

| 维度 | `backend/`（Python 1.0） | `app/`（Kotlin 2.0/3.0） |
|:--|:--|:--|
| **工具数量** | **23 个**（`tools/__init__.py:54-83`） | **6 个**（`NativeToolAgent.kt:49-199`） |
| **工具覆盖** | 天气、附近搜索、地理编码、地点模糊搜索、公交路线、骑行路线、网页搜索、记忆 CRUD ×6、日记读写 ×2、塔罗、日程 CRUD ×4、生理周期 ×3 | `open_app` / `click_element` / `input_text` / `swipe` / `task_finish` / `schedule_wake` —— **5 个代行工具 + 1 个闹钟，零生活工具** |
| **关心/主动性** | `agent/care.py`：深夜聊天 / 考前熬夜 / 消失 5 天后回来三类**异常感知关心**，带**冷却台账**（`COOLDOWN_HOURS = {late_night: 72h, event_combo: 24h}`），设计纪律明确写"**别每次都说必须由确定性状态保证，不能押在模型自觉上**" | 主动性有（`SilenceDecisionEngine` / `UnspokenThoughtManager` / `MotivationDynamics`），但**无"同一由头不唠叨"的台账机制** |
| **token 预算** | `utils/token_budget.py`（独立模块 + 测试） | 无对应物（`ChatHistoryTrimmer` 只是历史裁剪） |
| **DB 迁移纪律** | **v9 ~ v22 共 14 个迁移测试文件** | Room 仅 v1→v2，且 `RoomMigrationTest` 还带着错误基线 |
| **对"活人感"的贡献** | 高——她能查天气、记日程、想起你三天后考试、抽张塔罗 | 低——日常聊天里"帮你点屏幕"几乎用不上 |

我已在 `app/src/main` 全目录 grep 验证：**零命中** `天气|weather|web_search|塔罗|tarot|period|search_nearby|公交|骑行`。

**所以建议**：

1. 把 `backend/` 明确标注为**只读参考源，不再演进、不参与打包**（写进方案基线，替代"全仓 100% Native Kotlin"的表述）
2. **但加一张《待迁移能力清单》**（建议放 `docs/`），由 `backend/tools/__init__.py:54-83` 的 23 个工具 + `agent/care.py` 的关心机制 + `utils/token_budget.py` 逐条列出"已实现 / Android 侧有无对应 / 是否要迁"。否则这份参考源会慢慢腐烂成"没人知道它还能干什么"，而它恰好是**"活人感"最现成的素材库**
3. **其中 `agent/care.py` 建议优先迁**（见第八节批次 2）——它是我读完全仓后认为**单位成本收益最高的"活人感"改动**：三条检测规则 + 一张冷却表 + 一个纯函数，逻辑已在 Python 侧打磨过，且它的设计纪律（"别唠叨要由状态保证，不押在模型自觉上"）正是 Android 侧最缺的那条
